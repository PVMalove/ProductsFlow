# Support Service

Независимо разворачиваемый микросервис, отвечающий за **Службу поддержки, жизненный цикл тикетов и обратную связь**.

Сервис построен по принципам гексагональной архитектуры (Ports & Adapters) со строгим разделением слоев. Реализован паттерн **CQRS**, а логика роутеров сведена к "Тонким эндпоинтам", которые занимаются исключительно трансляцией HTTP-протокола. Разделяемые примитивы импортируются из `backend/libs/`.

## Ключевые обязанности
- **Управление тикетами**: Обрабатывает создание и переходы состояний обращений пользователей (`OPEN` → `IN_PROGRESS` → `RESOLVED` → `CLOSED`, терминальный статус).
- **Сообщения**: Цепочки сообщений внутри тикета; удаление сообщения — мягкое (текст заменяется маркером, позиция и автор в треде сохраняются).
- **Асинхронная хореография**: Локальный воркер (`support-worker`) слушает RabbitMQ на события `user.*.v1` от `identity-service`. По `user.deleted.v1` — анонимизирует ссылку на автора у его тикетов/сообщений и переводит его активные тикеты в `CLOSED` с системным сообщением.

## Архитектурные особенности
- **Проверка JWT — не через identity.** В отличие от `catalog-service`, support проверяет подпись токена **статически сконфигурированным публичным ключом** (`SUPPORT_JWT_PUBLIC_KEY`/`_PATH`), без единого сетевого обращения к identity. **Deny-by-default**: валидный токен без локальной проекции пользователя — `401`; известный, но неактивный/удалённый — `403`. Синхронного добора (в отличие от catalog) нет вовсе.
- **Transactional Outbox**: Мутации агрегатов `Ticket`/`TicketMessage` порождают события явным вызовом в `SqlTicketRepository`, в той же транзакции (Unit of Work), что и сама мутация — не через ORM-миксин.
- **Тонкие эндпоинты**: Контроллеры в `src/api/` занимаются только маппингом HTTP-структур в `Command`/`Query`-объекты, делегируя выполнение Хэндлерам, которые ничего не знают об HTTP.
- **Изолированное тестирование**: Юнит- и интеграционные тесты строго в границах своего сервиса; межсервисные сценарии — в общем `backend/tests/e2e/`.

## Команды разработчика

Все задачи выполняются через глобальный `Makefile` (Polyrepo), чтобы гарантировать использование правильного виртуального окружения (`uv.lock`):

```bash
# Запуск линтеров, форматтеров и статической типизации
make check pkg=support-service

# Запуск децентрализованных локальных юнит- и интеграционных тестов
make test pkg=support-service

# Автогенерация новой миграции БД
make db-revision pkg=support-service msg="add tickets table"
```

## Запуск

### Запуск через Docker (Production/Full Stack)
Весь стек (БД, брокеры, S3, все сервисы и Gateway) поднимается единой командой из корня ackend/:
``bash
make up_prod
``

### Локальный запуск (Разработка)
Для локальной отладки без Docker необходима запущенная инфраструктура.

1. Из корня ackend/ запустите PostgreSQL и RabbitMQ:
   ``bash
   make up_dev
   ``
2. Скопируйте .env.example в .env внутри директории support-service.
3. Находясь в директории support-service, примените миграции базы данных:
   ``bash
   uv run alembic upgrade head
   ``
4. Запустите сервис локально на порту 8003:
   ``bash
   uv run uvicorn src.api.main:app --port 8003 --reload
   ``
Swagger сервиса будет доступен по адресу: [http://localhost:8003/docs](http://localhost:8003/docs)
