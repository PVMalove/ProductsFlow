# 0032. Амендмент bootstrap-оркестрации (supersedes часть ADR 0017)

ADR 0017 описывало bootstrap-механизм (`*-bootstrap` one-off compose-сервисы, миграции → сид, `make dev pkg=<service>`) до того, как identity/catalog/support (#206–#209) реально его реализовали. `/grilling`-сессия, породившая эпик #205, свела код с текстом 0017 и обнаружила четыре расхождения. Здесь они фиксируются как решение, а не как ошибка реализации — 0017 остаётся верным описанием того, что было решено на момент своего написания.

**1. Три отдельных Postgres Compose-сервиса вместо внешнего провижининга.** 0017 не описывало явно, откуда берётся Postgres для каждого сервиса; `.env.example` до этого эпика указывал на `localhost:7610-7612` — БД предполагались поднятыми снаружи Compose. Реализация (#206/#207/#208) добавляет `identity-db`/`catalog-db`/`support-db` как обычные Compose-сервисы с `pg_isready`-healthcheck прямо в `backend/docker-compose.yml`, matching ADR 0010's «своя БД на сервис» изоляцию — не общий Postgres-инстанс и не внешняя ручная БД.

**2. Без Compose `profiles` на bootstrap-сервисах.** Профили рассматривались во время grilling как способ разделить «только миграции» и «миграции + сид» и отклонены: они не меняют нужное здесь поведение `depends_on` (`*-api`/`*-worker` всё равно ждут `*-bootstrap: service_completed_successfully` независимо от профиля) и добавляют флаг, который придётся помнить в каждом `docker compose up`. Разделение «только миграции» / «миграции + сид» решается на уровне `make setup`/`make demo` (см. ниже), не на уровне Compose-профилей.

**3. `OwnerReadModel` — через реальный событийный конвейер, не прямая запись.** 0017 буквально описывало сид catalog как прямую запись `OwnerReadModel(user_id=1, role=ADMIN, is_active=True)` в том же сид-скрипте, координируемую конвенцией `id=1` — под допущение, что `users.id` — автоинкремент. После #201 (identity-service) выяснилось, что `users.id` — `uuid.uuid4()`, автоинкрементного `id=1` не существует. Реализация (#207 identity, #208 catalog) заменяет прямую запись на реальный путь `user.registered.v1` → `identity-worker` → `catalog-worker` → `OwnerReadModel`, плюс новое аддитивное `user.role_changed.v1` для промоушена в admin; `catalog-bootstrap` дискаверит `user_id` ограниченным поллингом собственной `OwnerReadModel`-таблицы (`wait_for_admin_user_id`, `backend/services/catalog-service/src/api/bootstrap.py`) вместо чтения по фиксированному id. Advisory lock по-прежнему не нужен — независимость трёх bootstrap-шагов, которую 0017 обосновывало статичной конвенцией `id=1`, теперь опирается на то, что catalog сам ждёт появления строки, а не на факт совпадения id.

**4. `make setup`/`make demo` — новая пара поверх `make dev pkg=<service>`.** 0017 описывало только `make dev pkg=<service>` (миграция → `uvicorn --reload`, для локальной разработки одного сервиса). #209 добавляет `make setup` (поднять `*-db` + MinIO, дождаться health, прогнать `alembic upgrade head` для всех трёх сервисов — без сида, без `*-api`/`*-worker`) и `make demo` (`setup` как prerequisite, затем сид-шаг каждого сервиса: `python -m api.bootstrap` для identity/catalog, connectivity-check для support). `make setup demo` — обычный вызов `make` с двумя целями через пробел, `demo: setup` в качестве prerequisite; отдельного парсинга аргументов не потребовалось. `*-bootstrap`-сервисы в Compose остаются как были (одна команда `alembic upgrade head && python -m api.bootstrap`, issue #206/#207/#208) — `make setup`/`make demo` переопределяют команду через `docker compose run --rm --no-deps <service>-bootstrap <шаг>`, не меняя определение сервисов.

**5. RabbitMQ — добавлен как Compose-сервис; `identity-worker`/`catalog-worker` поднимаются внутри `make demo`.** Ни ADR 0017, ни эпик #205 не упоминали брокер явно — все `*_AMQP_URL` в `.env.example` указывали на внешний `localhost:5672`, как Postgres до пункта 1. Реальный прогон `make demo` (issue #209) вскрыл, что без брокера `identity-worker`/`catalog-worker` негде работать, а без них `catalog-bootstrap`'s поллинг `OwnerReadModel` (пункт 3) никогда не находит admin-пользователя и падает по таймауту. Решение: `backend/docker-compose.yml` получает сервис `rabbitmq` (`rabbitmq:4.1-management-alpine`, healthcheck через `rabbitmq-diagnostics ping`) в общей группе с `*-db`/`minio`, которую поднимает `make setup`; `make demo` дополнительно поднимает `identity-worker`/`catalog-worker` (`docker compose up -d --wait`) между сидом identity и сидом catalog — ровно на то время, что нужно поллингу catalog, но фактически они остаются запущенными и после (не гасятся отдельным шагом), так что окружение после `make demo` уже готово к `make up_prod`. `support-worker` в `make demo` не поднимается — сид support (connectivity-check) от проекции не зависит. Попутно исправлен путь монтирования тома `*-db` (`/var/lib/postgresql/data` → `/var/lib/postgresql`) — `postgres:18` отказывается стартовать на старом пути даже с пустым volume (docker-library/postgres#1259); без этого фикса `make setup` не проходил ни на одном из трёх `*-db` при первом реальном прогоне.

## Consequences

- `docs/adr/0017-migrations-seed-bootstrap.md` не переписывается — фиксирует решение на момент Фазы 0017/эпика #69, как было. Пункты 1, 3 и 4 выше помечают его superseded в соответствующих частях; пункт 2 (без `profiles`) подтверждает исходный текст 0017, а не меняет его.
- Независимость трёх bootstrap-шагов (0017: «не имеют `depends_on` друг на друга») сохраняется, но её механизм сменился с конвенции (`id=1`) на поллинг реального read-модели — если поллинг когда-нибудь заменится на sync-вызов между сервисами, эта независимость исчезнет вместе с ним (тот же риск, что 0017 уже называло для своей версии конвенции).
- `make setup`/`make demo` — единственный поддерживаемый способ поднять полное окружение с нуля; `make dev pkg=<service>` остаётся для работы над одним сервисом и не выполняет bootstrap других сервисов.
