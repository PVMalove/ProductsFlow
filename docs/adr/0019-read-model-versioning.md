# 0019. Версионирование read-моделей против гонки событий и синхронного добора

ADR 0012 ввёл второго писателя в read-модель пользователя (`OwnerReadModel` в catalog, `UserRefReadModel` в support) — синхронный добор на промахе холодного старта, наравне с консьюмером событий `user.*.v1`. Находки по `aio-pika` (issue #64) показали: `aio-pika` доставляет сообщения отдельными asyncio-задачами, порядок обработки внутри одного консьюмера не гарантирован даже при одном consumer'е. Без защиты устаревшее событие (`user.activated.v1`), обработанное позже более нового (`user.deactivated.v1`), может откатить запись к неверному состоянию — и то же самое может сделать сам добор, если он выполнится раньше события, которое уже было в пути.

**Перечитывание ADR 0012 сузило задачу вдвое.** Пишет в read-модель только «промах» — холодный старт, когда строки ещё нет. Админская ветка синхронной сверки (ADR 0012) ничего не пишет — это чтение для принятия решения по одному запросу, эфемерное. Гонка «второго писателя» существует только между консьюмером событий и одноразовой записью при создании строки, не при каждой админской проверке.

**Источник версии уже решён ADR 0014: `outbox_messages.id`.** Здесь фиксируется механика записи, не сам источник.

**`id` не дублируется в теле события.** `message.message_id` уже равен `outbox_messages.id` (зафиксировано в ADR 0015 ради идемпотентности по `processed_messages`) — консьюмер получает порядковый номер бесплатно из метаданных доставки AMQP, без изменения схемы payload.

**Read-модель хранит его в новой колонке `last_applied_outbox_id` и сравнивает атомарным upsert с условием, не read-затем-write в коде приложения.**

```sql
INSERT INTO owner_read_model (user_id, role, is_active, last_applied_outbox_id)
VALUES (:user_id, :role, :is_active, :incoming_id)
ON CONFLICT (user_id) DO UPDATE
SET role = EXCLUDED.role,
    is_active = EXCLUDED.is_active,
    last_applied_outbox_id = EXCLUDED.last_applied_outbox_id
WHERE owner_read_model.last_applied_outbox_id < EXCLUDED.last_applied_outbox_id;
```

Один SQL-запрос без окна между чтением и записью — обязательно, раз два события одного пользователя способны обрабатываться конкурентно в одном процессе (находки #64). Тот же приём, что монолит уже применяет для upsert картинки товара (`INSERT ... ON CONFLICT (product_id) DO UPDATE`, ADR 0009) — не новый паттерн для кодовой базы, а перенос уже принятого решения на новый случай.

**Версионируется вся строка одним номером, не поле за полем.** Все мутации агрегата `User` идут через один и тот же упорядоченный поток событий этого пользователя — `is_active` и `role` обновляются вместе при прохождении условия `WHERE`, раздельного версионирования по полям не требуется.

**Синхронный добор пишет строку с `last_applied_outbox_id = 0` при первом создании.** Реальные события несут `id ≥ 1` (bigserial), поэтому любое настоящее событие гарантированно проходит условие `0 < incoming_id` и корректно перезаписывает то, что добор создал при холодном старте. Две конкурентные попытки добора для одного и того же нового пользователя (оба находят строку отсутствующей, оба пишут `0`) сталкиваются на том же `ON CONFLICT` — второй запрос не проходит условие `0 < 0`, тихо не срабатывает, первый результат остаётся; расхождения в данных нет, поскольку оба добора читали одно и то же состояние `is_active`/`role` из identity почти одновременно. Контракт `GET /api/v1/users/me` из ADR 0012 (`id`, `role`, `is_active`) не меняется.

**Идемпотентность по `message_id` и версионирование по `outbox_id` — два разных, взаимодополняющих guard'а.** `processed_messages` защищает от повторной обработки **того же** сообщения (следствие At-Least-Once доставки, TD §5.1). Условие `last_applied_outbox_id <` защищает от применения **другого**, но более старого сообщения не в том порядке. Обе проверки выполняются в одной транзакции консьюмера — TD уже требует этого для Idempotent Consumer в целом («применение эффекта и вставка в `processed_messages` — в одной транзакции»), здесь read-model upsert просто занимает место «применения эффекта».

## Considered Options

- **Read-then-compare-then-write в коде приложения** — читаемее построчно, но два раунд-трипа вместо одного оставляют окно гонки ровно там, где она реальна: между конкурентными asyncio-задачами одного консьюмера. Отклонено.
- **Отдельный счётчик версии на агрегате `User`, инкрементируемый в identity** — рассмотрен и отклонён ещё в ADR 0014 как избыточный при уже имеющемся монотонном `outbox_messages.id`; здесь не пересматривается.
- **identity расширяет `/users/me` четвёртым полем — актуальным `outbox_messages.id` пользователя** — отклонено в пользу сентинела: даёт полную симметрию с событийным путём, но меняет уже зафиксированный контракт ADR 0012 и требует от identity читать собственную outbox-таблицу вне её основного назначения (публикации) ради синхронного пути, которого TD в явном виде не описывает.
- **Fallback ставится «ниже» через `WHERE last_applied_outbox_id IS NULL`** (пишет только если строки совсем нет, вместо upsert с сентинелом) — семантически то же самое, но без единого механизма с событийным путём: два разных условия в двух разных местах кода вместо одного условия `<` везде. Отклонено ради единообразия.
- **Версионирование по отдельным полям** (`is_active_version`, `role_version`) — отклонено: агрегат `User` не допускает независимой эволюции `is_active` и `role` вне общего потока событий, раздельные версии решали бы проблему, которой не существует.

## Consequences

- `OwnerReadModel` и `UserRefReadModel` получают новую колонку `last_applied_outbox_id` (bigint, not null, default 0) — не входит в исходный список полей TD (`user_id, role, is_active`), необходимое дополнение схемы.
- Порядок обработки событий одного пользователя больше не обязан быть гарантирован ни на уровне брокера, ни на уровне консьюмера — корректность держится на upsert-условии, а не на дисциплине доставки. Согласуется с находками #64: RabbitMQ и `aio-pika` этой гарантии и не дают.
- Строка с `last_applied_outbox_id = 0`, если так и не подтверждённая ни одним реальным событием (пользователь существует в identity, но `user.registered.v1` почему-то не дошло), навсегда остаётся легитимно перезаписываемой — это не баг, а следствие того, что `0` специально спроектирован как «всегда проигрывающая» версия.
- Идентичный upsert-паттерн теперь используется дважды в проекте (ADR 0009 — картинка товара, здесь — read-модели пользователя) — кандидат на обобщение в `common-kernel`, если появится третий подтверждённый потребитель (admission-правило ADR 0013), не раньше.
