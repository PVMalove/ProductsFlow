# BFF API response envelope

All new and migrated BFF endpoints return successful payloads as `{\"data\": T, \"meta\": {}}` and expected failures as `{\"error\": {\"code\": string, \"message\": string}}`. Each service owns a framework-independent `src/contracts` layer of frozen dataclasses: application handlers return those DTOs, while HTTP only serializes them. Request schemas remain in `api.schemas`; body-less commands use a Pydantic path dependency that exposes `to_command(actor=...)`.

`kernel-platform` owns generic Result-to-HTTP translation and global exception handlers. It must not depend on service DTOs; expected service exceptions expose `code`, `message`, and `status_code` structurally, while domain `Result.error` supplies its own code and `ErrorType`. FastAPI HTTP and validation errors receive standard BFF codes, and unknown failures are logged but exposed only as a safe 500 `INTERNAL_ERROR` response. `match_created` makes creation explicit in a router but the route decorator remains the sole owner of HTTP 201. Migrated update, activation, deactivation, and deletion endpoints deliberately use HTTP 200 rather than 204 so every command response can carry the envelope; deletion returns `data: null`.

This is a deliberate breaking contract change that gives BFF clients one stable parsing model while preserving service-layer ownership of DTO conversion. `code` is for machine decisions and `message` is human-readable. The first migration is limited to catalog product commands; their success responses are enveloped, while query and product-image success responses remain flat until their own reviewable migrations. Error responses change to the BFF shape across catalog immediately.
