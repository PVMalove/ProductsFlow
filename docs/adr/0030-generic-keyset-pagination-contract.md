# 0030. Общий keyset-пагинационный контракт в kernel-platform

ADR 0001/ADR 0005 закрепили курсорную (keyset) пагинацию для листингов изменяемых сущностей, но сам контракт — непрозрачный курсор, форма страницы (`has_more`/`has_prev` и т.п.) и кодирование/декодирование курсора в base64-строку — остался целиком локальным `catalog-service` (`domain/repositories.py`, `application/pagination.py`, `infrastructure/db/pagination.py`). Epic #198 (`identity-service: полная реализация`, TD-01 Фаза 2) вводит листинг `User` (issue #201/#202) на той же keyset-схеме — второй подтверждённый потребитель, который делает дальнейшее дублирование неоправданным (тот же admission-принцип ADR 0013, уже применённый в ADR 0029 к generic drain-в-outbox — issue #199 из того же epic). Issue #200 выполняет обобщение и мигрирует единственного уже существующего потребителя (`catalog-service`); подключение `identity-service` — самостоятельные PR эпика (issue #201/#202), вне рамок этого ADR.

**Решение.** `kernel_platform.pagination` — новый flat-модуль (по образцу уже существующих `consumer.py`/`topology.py`, не подпакет: контракт умещается в один небольшой файл) с шестью экспортами: `DEFAULT_PAGE_LIMIT`/`MAX_PAGE_LIMIT` (те же значения, 20/100), `InvalidCursorError`, `Cursor` (frozen dataclass — `created_at: datetime`, `id: uuid.UUID`), `PageInfo` (frozen dataclass — `next_cursor`/`prev_cursor`/`has_more`/`has_prev`) и `encode_cursor`/`decode_cursor`. Модуль зависит только от stdlib (`base64`, `uuid`, `datetime`) — как и остальной `kernel-platform`, никакого нового пакетного requirement.

`catalog-service`'s `domain/repositories.py` больше не объявляет `Cursor`/`PageInfo` как собственные dataclass — они импортируются из `kernel_platform.pagination` и используются в контракте `ProductRepository`/`ProductPage` без изменений по форме. `application/pagination.py` и `infrastructure/db/pagination.py` (последний — уже помеченный как compatibility-реэкспорт для инфраструктурных тестов) удалены целиком: оба стали чистыми проходными модулями без единого прямого потребителя за пределами тестов. Оставшиеся два прямых потребителя кодека — `infrastructure/db/product_repository.py` (`encode_cursor`) и `api/products.py` (`DEFAULT_PAGE_LIMIT`/`MAX_PAGE_LIMIT`/`Cursor`/`InvalidCursorError`/`decode_cursor`) — импортируют напрямую из `kernel_platform.pagination`. Модульные тесты кодека (`test_encode_decode_roundtrip` и т.д.) переехали в `kernel-platform/tests/unit/test_pagination.py`; `catalog-service`'s интеграционный тест репозитория (`test_product_repository.py`) правит только источник импорта `decode_cursor`, само поведение не проверяется по-новому.

`domain/repositories.py`, импортируя `kernel_platform.pagination`, формально пересекает слой: `check_architecture.py` (ADR 0028) запрещает `domain`/`application` импортировать `infrastructure`/`api`/`fastapi`/`sqlalchemy`, но не `kernel_platform` — тот же прецедент, что и `kernel_domain.result.Result` уже используемый в этом файле. `kernel_platform.pagination` не тянет ни SQLAlchemy, ни FastAPI — чистый stdlib-контракт, поэтому такое пересечение не нарушает ни букву, ни дух ADR 0028: `check_architecture.py --strict` проходит без findings.

## Considered Options

- **Оставить `Cursor`/`PageInfo` в `kernel_domain`, а не в `kernel_platform`** — отклонено: issue #200 и epic #198 прямо формулируют решение как переезд в `kernel-platform` («аналогично [generic drain-в-outbox], курсорная пагинация... переезжает в kernel-platform»), симметрично уже принятому ADR 0029 месту для родственного generic-контракта. Пересматривать это в рамках рефакторинга, помеченного «поведенчески нейтральный», нет оснований.
- **Подпакет `kernel_platform/pagination/` (по аналогии с `outbox/`, `security/`)** — отклонено: контракт — один файл на полсотни строк без внутреннего разделения на несколько модулей, подпакет добавил бы структуру без наполнения. `consumer.py`/`topology.py` — уже существующий в этом же пакете прецедент flat-модуля такого размера.
- **Сохранить `application/pagination.py`/`infrastructure/db/pagination.py` как тонкие compatibility-реэкспорты** (по образцу самого `infrastructure/db/pagination.py` до этой задачи) — отклонено: AC issue #200 прямо требует использования общего типа «вместо локальной копии»; оставление реэкспорт-модулей без единого прямого продакшен-потребителя не даёт ничего сверх лишнего файла и лишней точки для расхождения при будущих правках.
- **Обобщить заодно и `ProductPage`** (контейнер `items: list[T]` + `page_info: PageInfo`, generic по образцу `kernel_domain.Result[T]`) — отклонено: AC issue #200 перечисляет только тип курсора, форму страницы (`PageInfo`) и кодек; `ProductPage` не упомянут, и вводить общий generic-контейнер под гипотетического будущего потребителя (не подтверждённого использованием, всего один существующий вызывающий — `ProductPage`) нарушило бы тот же admission-принцип ADR 0013, применённый в обратную сторону — обобщение без второго факта использования.

## Consequences

- Второй потребитель того же контракта (`identity-service`/`User` — issue #201/#202) подключается, только импортируя `kernel_platform.pagination`, без нового кода в `kernel-platform` и без копирования кодека.
- `catalog-service`-тесты (юнит и интеграционные, включая репозиторий, HTTP API и пагинацию) остаются зелёными без изменения ожидаемого поведения — рефактор поведенчески нейтрален, как и требовали Acceptance Criteria issue #200; `python backend/scripts/check_architecture.py --strict` подтверждает отсутствие новых layer-violations.
- `support-service`/`SqlTicketRepository`'s собственный `application/pagination.py` (независимо заведённый для `Ticket`, до этой задачи) не переводится на общий контракт — вне рамок issue #200 (см. Out of Scope epic #198), как и аналогичное решение ADR 0029 для того же сервиса.
