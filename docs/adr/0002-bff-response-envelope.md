# 0002. BFF API: единый конверт ответа

**Статус:** Accepted

Все бизнесовые эндпоинты `/api/v1` трёх сервисов отдают ответ в одном формате.

Успех — объект:

```json
{
  "data": { "id": "a1b2c3d4-...", "name": "Пример товара" },
  "meta": {}
}
```

Успех — список (пагинация — только в корневом `meta`, не внутри элементов `data`):

```json
{
  "data": [
    { "id": "a1b2c3d4-...", "name": "Товар 1" },
    { "id": "e5f6a7b8-...", "name": "Товар 2" }
  ],
  "meta": {
    "next_cursor": "eyJjcmVhdGVkX2F0IjogIi4uLiJ9",
    "has_more": true
  }
}
```

Ожидаемая ошибка (детали трансляции — [ADR 0003](0003-centralized-error-handling.md)):

```json
{
  "error": { "code": "PRODUCT_NOT_FOUND", "message": "Товар не найден" }
}
```

`code` — для машинного решения на клиенте, `message` — для человека. Для ошибок валидации конверт может дополнительно содержать `details`: упорядоченный массив `{ "field": "items.0.price", "issue": "…" }`. `field` опускается для ошибки формы без отдельного поля. Этот массив используется одинаково для domain-валидации и Pydantic request-validation; подробности трансляции определяет ADR 0003/0014. Конверт покрывает все бизнесовые эндпоинты без исключений: команды, запросы, картинку товара, audit-фиды.

## HTTP-статусы

- **Создание — `201`**, единственный статус-код, для которого декоратор роутера остаётся единоличным владельцем (`@router.post(..., status_code=201)`).
- **Все прочие успешные мутации (обновление, активация/деактивация, удаление) — `200`, не `204`.** `204` не оставляет места для тела ответа, поэтому не используется вовсе. Удаление (включая логическое удаление сообщения тикета) возвращает:

  ```json
  {
    "data": null,
    "meta": {}
  }
  ```

- Список — `data` содержит массив View; метаданные пагинации — только в корневом `meta`, не внутри элементов массива. Для составных ответов (например, детальная карточка тикета вместе с первой страницей его сообщений) пагинация вложенной коллекции — тоже в корневом `meta` ответа, не в самом View.

## Контрактные слои

Каждый сервис владеет framework-independent слоем `src/contracts` — frozen dataclasses (View). Application-хендлеры возвращают эти DTO в `Result[View]`; HTTP-слой только сериализует их в конверт, не строит их сам. Request-схемы остаются в `api/schemas` (Pydantic); body-less команды (path/query без JSON-тела) используют Pydantic path-зависимость, экспонирующую `to_command(actor=...)`/`to_query(actor=...)` — параметры URL не собираются вручную в роутере (см. также «тонкие роутеры» — [ADR 0006](0006-service-internal-architecture-baseline.md)).

**Роутер не оркестрирует несколько use case.** Один HTTP-эндпоинт — один вызов одного command/query handler'а; составной ответ (например, детальная карточка тикета вместе с первой страницей сообщений) собирается одним query, а не последовательностью из нескольких вызовов handler'а внутри роутера.

## Исключения из BFF-конверта

Не всякий HTTP-эндпоинт — BFF API. Плоскими остаются:

- JWKS (`/.well-known/jwks.json`) — открытый инфраструктурный протокол, не бизнес-ответ.
- Health checks.
- Внутренние worker-триггеры.
- `POST /api/v1/auth/login` — стандартный OAuth2 `password`-grant для `OAuth2PasswordBearer`/Swagger UI; форма ответа диктуется спецификацией OAuth2, не BFF-конвенцией.

## Considered Options

- **Оставить `204` для удаления** — отклонено: `204` не несёт тела, а BFF-контракт требует единого конверта на каждый ответ без исключений; `200 {"data": null}` даёт то же семантическое «нет содержимого», не ломая единообразие парсинга на клиенте.
- **`/api/v2` вместо breaking-изменения существующего `/api/v1`** — отклонено; см. [ADR 0004](0004-api-gateway-and-routing.md) за полным обоснованием единой версии API.

## Consequences

- Интеграционные HTTP-тесты проверяют статус и итоговый BFF-конверт целиком, а не детали внутренних вызовов handler'ов.
- Любой новый бизнесовый эндпоинт по умолчанию обязан отдавать конверт с первого дня.
