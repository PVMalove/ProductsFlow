# 0005. Безопасность: RS256/JWKS, единый контракт `Actor`, RBAC

**Статус:** Accepted

## Выпуск и проверка токена

`identity-service` — единственный держатель приватного ключа и единственный поставщик истины о личности. Токены — stateless JWT, RS256, с `sub`/`iat`/`exp`/`iss`; `kid` — JWK thumbprint (RFC 7638), детерминированно выводится из самого ключа, стабилен между рестартами и одинаков у всех реплик. `aud` не вводится — все сервисы сейчас равноправные получатели. Приватный ключ — файл по `IDENTITY_JWT_PRIVATE_KEY_PATH`, том монтируется только в identity; `make keys` генерирует dev-пару, в git не попадает, CI генерирует эфемерную пару на прогон. При `APP_ENV=prod` пустой приватный ключ/JWKS-URL/`DATABASE_URL`/`ADMIN_PASSWORD` валит старт сервиса fail-fast; в dev дефолты допускаются ради «склонировал и запустил».

identity публикует `GET /.well-known/jwks.json` — открытый, без аутентификации (публичный ключ не секрет).

## Проверка токена расходится по сервисам

- **`catalog-service`** проверяет подпись через `kernel_platform.security.IdentityClient.verify_token()` — JWKS-кэш с TTL 10 минут, внеочередной refetch при неизвестном `kid` с троттлингом 60 секунд против усиления запросов к identity. Тот же клиент используется для синхронного добора `fetch_current_user()` ([ADR 0011](0011-catalog-service-event-integration.md)).
- **`support-service`** проверяет подпись локальным, статически сконфигурированным публичным ключом (`SUPPORT_JWT_PUBLIC_KEY`/`SUPPORT_JWT_PUBLIC_KEY_PATH`) — не обращается к JWKS-эндпоинту identity и не использует `IdentityClient` для этого пути вовсе. Причина: требование к support — полностью stateless auth без сетевой проверки на горячем пути. Плата — ротация ключа identity требует ручного обновления конфигурации `SUPPORT_JWT_PUBLIC_KEY`/`_PATH` в support (в отличие от catalog, где кэш сам переспросит по новому `kid`).

Та же асимметрия продолжается в синхронных точках поверх read-моделей: catalog делает синхронный добор к identity на промахе read-модели и на админской ветке ([ADR 0011](0011-catalog-service-event-integration.md)); support не делает ни одного синхронного вызова к identity — вместо этого **deny-by-default**: валидный JWT без локальной строки проекции — `401 UNAUTHENTICATED`, известный, но неактивный/удалённый пользователь — `403 FORBIDDEN` ([ADR 0012](0012-support-service-event-integration.md)). Оба расхождения (проверка подписи и синхронный добор) — одно архитектурное решение support: нулевая сетевая зависимость от identity на горячем пути запроса, ценой того, что окно эскалации/устаревания у него закрывается консервативным отказом, а не подтверждением через сеть.

## Единый `Actor`

`Actor`/`ActorRole` — framework-independent frozen contracts в `kernel_platform.security`, не service-local дубликаты. Security-зависимость эндпоинта **аутентифицирует** запрос и строит `Actor(id, role)` из проверенного токена; **авторизацию** конкретного действия выполняет handler, возвращая `Result.err(FORBIDDEN)` при отказе — эти две ответственности не смешиваются в одном месте.

`/users/me` (identity) не доверяет claims токена как источнику ответа: JWT-зависимость строит transport-neutral `Actor`, а `GetCurrentUserHandler` сверяет его с актуальным состоянием `User` в БД и возвращает `Result[UserView]` — устаревший токен с уже неверной ролью не может представиться через `/users/me` тем, кем пользователь больше не является.

Actor, зафиксированный как инициатор действия в audit-логе identity/catalog ([ADR 0007](0007-identity-service-domain-model.md), [ADR 0008](0008-catalog-service-domain-model.md)), при отсутствии HTTP-контекста (саморегистрация, сидирование) равен самому затронутому пользователю или владельцу товара — отдельный системный Actor не заводится.

## Request context и логирование

Один ASGI-middleware (`observability.RequestContextMiddleware`) устанавливает контекст запроса для всех трёх сервисов разом: читает `X-Request-ID` (иначе генерирует), выставляет `request_id_var`; принимает `TokenVerifier` (JWKS-based у catalog, статический ключ у support, локальный verifier у identity) и, если bearer валиден, выставляет `actor_id_var` — тот же ContextVar, который читает и audit-лог, и структурный JSON-лог запроса (`method`, `path`, `status_code`, `duration_ms`). Отсутствие/невалидность токена не блокирует запрос на этом уровне — актуальная авторизация эндпоинта проверяется отдельно, эта прослойка только для audit/логов. `trace_id`/`span_id` зарезервированы в схеме лога как `null` — OTEL SDK не подключён; заполнение этих полей будущей инструментацией не требует переписывать middleware или форматтер.

## RBAC и видимость

Форма политики видимости — общий `kernel_domain.VisibilityPolicy`-протокол ([ADR 0006](0006-service-internal-architecture-baseline.md)); реализации локальны для каждого сервиса против своей read-модели (правила — [ADR 0008](0008-catalog-service-domain-model.md)/[0009](0009-support-service-domain-model.md)).

## Considered Options

- **JWKS для support, как и для catalog** — отклонено действующим требованием support «нулевая сетевая зависимость на горячем пути»: JWKS-refetch — сетевой запрос к identity при промахе кэша, несовместимый с этим требованием сильнее, чем для catalog, у которого сетевой вызов к identity уже есть по другой причине (админская сверка).
- **Синхронный добор для support по аналогии с catalog** — отклонено: deny-by-default проще устраняет то же окно эскалации привилегий при более простой реализации (без исключения по типу пользователя/операции), ценой чуть большей задержки видимости изменений для новых пользователей — задержки, равной времени доставки события.

## Consequences

- Два разных читателя кода одного и того же класса функциональности (JWT-проверка) увидят два разных механизма в зависимости от того, какой сервис они открыли — расхождение задокументировано здесь и не должно устраняться «выравниванием» одного сервиса под другой без отдельного решения.
- Support не имеет `503`-деградации при недоступности identity (нет синхронного пути к нему вовсе) — единственная его зависимость от identity в рантайме рабочего запроса — своевременная доставка событий через RabbitMQ.
- Баг в `RequestContextMiddleware` эквивалентен потере `request_id`/`actor_id`/access-log сразу во всех трёх сервисах.
