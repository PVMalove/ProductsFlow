# 0014. Коллекции доменных ошибок и детали ошибок в BFF

**Статус:** Accepted

Доменный `Result.err` по-прежнему несёт один объект `Error`, однако множественные нарушения одной операции представляются `ErrorList`, наследующим `Error`. `ErrorList` сохраняет тип `VALIDATION`, код `general_multiple_validation_errors` и включает только дочерние validation-ошибки с кодом, описанием и `invalid_field`. Его фабрика запрещает пустую коллекцию, возвращает единственную простую ошибку без обёртки и разворачивает вложенные списки в плоскую коллекцию с сохранением порядка и повторов. Это позволяет ядру сохранить совместимость с `Result[T]`, а агрегатам вернуть все независимые нарушения за одну проверку. `ErrorType.FORBIDDEN` остаётся частью контракта: это необходимая семантика отказа в доступе и HTTP 403 из ADR 0003.

Публичный BFF-конверт ошибки расширяется опциональным полем `error.details`. Когда ошибка является `ErrorList`, `details` содержит элементы `{ "field": <invalid_field>, "issue": <description> }`; `field` опускается для ошибки без конкретного поля, а при единичной ошибке `details` не передаётся. `invalid_field` всегда является публичным `snake_case`-именем JSON-поля, а не внутренним именем атрибута. `RequestValidationError` FastAPI также формируется в этот массив из `loc` и `msg`, поэтому Pydantic-валидация с HTTP 422 и доменная валидация с HTTP 400 имеют единую форму для клиента. Это намеренное расширение совместимого конверта из ADR 0002/0003: UI получает точную привязку ошибок к полям, а клиенты, читающие только `code` и `message`, продолжают работать.

Миграция затрагивает только ожидаемые `Result`-ошибки в domain и application слоях всех сервисов. Технические исключения инфраструктуры, API-адаптера и их обработка остаются отдельным путём. Ожидаемая доменная валидация не использует `ValueError`: методы возвращают `Result.err`, и каждый метод накапливает все независимые нарушения в `ErrorList`. Каждый сервис владеет одним `domain/errors.py` с классом `[Service]Errors`, которым пользуются domain и application, но не infrastructure. Стабильные BFF-коды не меняют существующий `snake_case`-формат; реестры ошибок устраняют сырые конструкторы, но не являются поводом для breaking change кодов. Публичные `description` содержат только безопасный стабильный текст и не отражают пользовательские либо технические значения. Одиночный `Error` сохраняет `||`-формат, но отказывается сериализовать значения с разделителем, чтобы исключить потерю данных. `ErrorList` сериализуется строго как JSON-объект `{ "errors": [{ "code", "description", "type", "invalid_field" }] }`; его фиксированные metadata восстанавливаются при десериализации. `Error.deserialize()` полиморфно распознаёт этот формат наряду с сохранённым `||`-форматом одиночного `Error`.

## Considered Options

- Оставлять наружу только `General.MultipleValidationErrors` — отклонено: клиент не может определить, какие поля должны быть исправлены.
- Менять `Result[T]` на коллекцию ошибок — отклонено: это затрагивает ядро и все потребители существенно шире, чем адаптер `ErrorList`.
- Мигрировать технические исключения в `Result` — отклонено: это смешивает ожидаемый бизнес-отказ с непредвиденным сбоем инфраструктуры.
- Перевести существующие коды в PascalCase — отклонено: `code` является публичным BFF-контрактом, а новый формат не даёт ценности, оправдывающей breaking change.
- Отдавать отдельные формы валидации Pydantic и domain — отклонено: клиенту не должна быть видна реализация границы, на которой ошибка была обнаружена.
- Дедуплицировать ошибки во время нормализации — отклонено: порядок и повтор нарушения являются фактами валидации; решение о представлении остаётся клиенту.
