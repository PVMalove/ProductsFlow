# 0015. Топология RabbitMQ: exchange, очереди, retry-лестница, DLQ

TD требует явную топологию RabbitMQ с DLX и предупреждает в таблице рисков: имена exchange/очередей проверить перед Фазами 4–5, прежде чем на них появятся внешние потребители. Находки по `aio-pika` (issue #64) дали фактуру, которая многое здесь предрешает: **классические очереди не поддерживают лимит попыток на уровне брокера вовсе** («Classic queues do not support poison message handling») — только quorum-очереди дают `x-delivery-limit`. TD требует «лимит попыток → DLQ» буквально, поэтому тип очереди — `quorum`, не предмет выбора.

**Exchange.** `productsflow.events`, тип `topic`, durable. Объявляется identity на старте — единственный продюсер.

**Routing keys** — из TD буквально: `user.registered.v1`, `user.activated.v1`, `user.deactivated.v1`, `user.role_changed.v1`.

**Основные очереди — по одной на сервис, wildcard-биндинг.** `catalog.user-events` и `support.user-events`, обе quorum, обе привязаны к `productsflow.events` паттерном `user.*.v1`. Catalog и support применяют все четыре типа события к одной и той же read-модели (`OwnerReadModel`/`UserRefReadModel`) — деление на очередь-на-тип разнесло бы события одного пользователя по независимым консьюмерам без гарантии взаимного порядка, что подорвало бы предпосылку issue #71/ADR 0014 (порядок по `outbox_messages.id` работает только внутри одного канала доставки).

**DLQ — общий DLX, отдельная очередь на сервис.** Один exchange `productsflow.dlx` (direct); `catalog.user-events.dlq` и `support.user-events.dlq` привязаны к нему собственным routing key, совпадающим с именем основной очереди. Общая очередь смешала бы отравленные сообщения двух сервисов — при разборе пришлось бы каждый раз заглядывать в тело, чтобы понять, чей консьюмер сломался.

**Retry-лестница — три TTL-очереди на сервис, не настоящий exponential backoff.** TD дословно требует «Retry с Exponential Backoff», но находки #64 показывают: полноценный экспоненциальный backoff нуждается в наборе retry-очередей — по одной на интервал, иначе одна очередь с разнородным `expiration` на сообщениях даёт head-of-line blocking (сообщение с задержкой 5с застревает за сообщением с задержкой 10 минут). Учитывая, что ожидаемые сбои здесь транзиентные (блип БД при записи read-модели, не многочасовой отказ), три ступени — компромисс, читаемый в коде и достаточный по факту: `catalog.user-events.retry.5s`, `.retry.30s`, `.retry.2m` (аналогично для support). Внутри каждой ступени TTL однороден — head-of-line blocking не возникает.

**Механизм ступеней — управляется консьюмером, не declarative DLX-цепочкой.** Статический `x-dead-letter-routing-key` на очереди не может каждый раз указывать на разную ступень — выбор ступени зависит от номера попытки. Схема:

1. При исключении в обработчике консьюмер читает `x-death` (массив, который брокер ведёт сам — см. находки #64 §3.3) и считает попытки для своей очереди.
2. Если попыток меньше трёх: консьюмер публикует сообщение напрямую в очередь нужной ступени (через безымянный default exchange, routing key = имя ступени-очереди — доставка в одну конкретную очередь без топик-fanout) и **ack'ает** исходную доставку, а не `reject`. `reject` здесь не используется, потому что сработал бы статический DLX основной очереди.
3. Ступень-очередь по истечении своего TTL дед-леттерится через default exchange обратно в **свою же** основную очередь того же сервиса (routing key = имя основной очереди) — никогда не в топик-exchange, чтобы не разослать retry фанаутом обоим сервисам.
4. Если попыток уже три (ступени исчерпаны): консьюмер делает `reject(requeue=False)` — срабатывает статический `x-dead-letter-exchange`/`x-dead-letter-routing-key` основной очереди, сообщение уходит в `productsflow.dlx` → свою DLQ.
5. `x-delivery-limit` на основной quorum-очереди выставлен генерозно (RabbitMQ-дефолт с версии 4.0 — 20) как страховка от бага в подсчёте ступеней консьюмером, не как основной механизм завершения.

**Объявление топологии — идемпотентно на старте, без отдельного deploy-шага.** identity объявляет `productsflow.events` при старте; catalog и support объявляют свои основные, ступенчатые и DLQ-очереди вместе с биндингами при своём старте. `declare_exchange`/`declare_queue` в `aio-pika` идемпотентны при совпадающих параметрах — повторный вызов с теми же аргументами не создаёт новый объект, `PRECONDITION_FAILED` бросается только при расхождении параметров. ADR 0010 уже вынес миграции Postgres в отдельный one-off compose-шаг из-за гонки при нескольких репликах API — у RabbitMQ-топологии этой гонки нет: `declare_*` безопасен к повторным параллельным вызовам, третий deploy-концепт (вслед за Postgres-миграциями и `ensure_minio_buckets`) не оправдан.

**`message_id`.** Равен `id` строки `outbox_messages` (ADR 0014) — уже отмечено в наброске консьюмера в находках #64. Обеспечивает идемпотентность по `processed_messages` без отдельного механизма.

**Версионирование событий (`.v1` → `.v2`).** Не реализуется сейчас — TD ещё не вводит `v2` ни для одного события. Зафиксирована только конвенция на будущее: новая версия схемы события — это новый routing key (`user.activated.v2`), не новый exchange. Когда `v2` появится, биндинг основной очереди расширяется с `user.*.v1` до `user.*.*` (или добавляется второй биндинг), а консьюмер различает версию по routing key/полю в payload. Спекулятивной инфраструктуры под это не заводится — правило существует только как задокументированное намерение.

## Considered Options

- **Полноценный экспоненциальный backoff (N растущих очередей)** — отклонено: находки #64 прямо показывают цену (N очередей и N биндингов вместо трёх) ради сбоев, которые ожидаются транзиентными. Три ступени дают то же качественное поведение («растущая пауза, потом сдаёмся») за кратно меньшую сложность.
- **Одна retry-очередь с фиксированным TTL, лимит попыток только через `x-delivery-limit`** — отклонено: пауза не растёт со временем, расходится с формулировкой TD сильнее, чем лестница, при сопоставимой сложности реализации.
- **Без retry — сразу в DLQ на первое же исключение** — отклонено: не прощает ни одного транзиентного сбоя БД, а такие сбои — ожидаемый нормальный случай для read-модели, синхронизируемой событиями.
- **Общая DLQ на оба сервиса** — отклонено: неудобство при разборе завалов перевешивает экономию одной очереди.
- **Очередь на тип события вместо очереди на сервис** — отклонено: разносит события одного пользователя по независимым консьюмерам без гарантии взаимного порядка, подрывая предпосылку ADR 0014 о том, что порядок по `outbox_messages.id` работает внутри одного канала доставки.
- **Отдельный one-off deploy-шаг для топологии RabbitMQ, по аналогии с Postgres-миграциями** — отклонено: у идемпотентного `declare_*` нет гонки при нескольких репликах, которая оправдывала вынос миграций в ADR 0010. Введение третьего deploy-концепта не даёт защиты, которую не даёт уже идемпотентность.
- **Ступень-возврат через общий топик-exchange с сохранением исходного routing key** — отклонено: топик-exchange разослал бы возвращённое сообщение всем подписчикам с совпадающим биндингом (и catalog, и support), а не только тому сервису, чей консьюмер изначально не справился.

## Consequences

- Консьюмер несёт логику подсчёта попыток и явной маршрутизации по ступеням (чтение `x-death`, публикация в конкретную ступень-очередь, `ack` вместо `reject` на промежуточных попытках) — это не declarative-конфигурация одной очереди, а код, который пишется и тестируется как часть issue #66/#67 реализации (Фаза 2b/4/5).
- `x-delivery-limit` как страховочный, а не основной механизм означает: баг в подсчёте ступеней проявится не мгновенным зависанием, а сообщением, которое переживает больше повторов, чем задумано лестницей, прежде чем брокер вмешается сам.
- Три конкретных TTL (5с/30с/2мин) — тюнинг-параметры, не архитектурное решение; меняются без пересмотра этого ADR.
- Наблюдаемость DLQ (глубина очереди, возраст самого старого сообщения) — предмет Фазы 9, за границей destination; здесь фиксируется только форма очередей, на которые эти метрики будут смотреть.
- Расширение на `v2` требует ручного обновления биндинга и кода консьюмера при появлении второй версии события — процесса автоматической совместимости не вводится, это осознанно отложено до момента, когда `v2` реально появится.
