# 0018. Разнесение существующих тестов по сервисам

`tests/` монолита — 7 интеграционных файлов на testcontainers (5057 строк) и 5 unit-файлов. Прямой перенос по имени файла невозможен: часть тестов проверяет логику, которая после ADR 0011/0013/0016 физически переехала в `kernel-platform`; часть — инвариант, который после распила держат два сервиса и событие, а не один SQL JOIN; `support` не покрыт тестами вообще, ни одним файлом.

**~46 тестов «товары деактивированного владельца скрыты» переписываются как E2E-сценарии Фазы 6.** Все, дословно, а не выборочно — каждый из перечня в `test_product_e2e.py`/`test_product_repository.py` (`test_get_products_page_hides_matches_of_deactivated_owners_by_default` и его варианты по list/search/category/price-range, плюс admin-ветка) становится полным межсервисным сценарием через реальный identity + RabbitMQ, а не облегчённой версией, проверяющей read-модель напрямую. Осознанная цена — медленнее и избыточно (одна и та же проверка «событие дошло → read-модель обновилась → видимость изменилась» повторяется на разных эндпоинтах), принятая ради того, чтобы поведение было доказано сквозным путём, а не по частям.

**Фаза 3 закрывает свой собственный DoD отдельным, свежим набором тестов — не миграцией старых 46.** TD требует «Unit-тесты на все ветки видимости» как часть DoD именно Фазы 3, до того как Фаза 6 вообще начнётся. Это не тот же вопрос, что миграция старых интеграционных тестов: новый набор сеет `OwnerReadModel` напрямую в тестовой БД catalog (тот же приём, что ADR 0017 использует для сида — не через событие) и проверяет политику видимости изолированно, без RabbitMQ и без identity. Обе группы тестов сосуществуют и проверяют разное: свежий набор Фазы 3 — саму политику; E2E Фазы 6 — что событие реально доставляет то состояние, которое политика ожидает.

**Тесты синхронного fallback (ADR 0012) — отдельная категория, не часть вопроса про 46.** `test_admin_can_still_update_a_deactivated_owners_product` и подобные admin-тесты проверяют не read-модель, а факт синхронного вызова `IdentityClient`/`TokenVerifier` для админ-ветки. Catalog тестирует это локально с фейковым `TokenVerifier`/`IdentityClient` (тестовый двойник, возвращающий нужную роль) — не требует ни реального identity, ни события.

**Новая dev-only библиотека `libs/test-support`.** Четвёртый член workspace, только в `[dependency-groups] dev` каждого сервиса — не production-зависимость, поэтому admission-правило ADR 0013 (домены/kernel-platform, «минимум два подтверждённых потребителя production-кода») к ней не применяется буквально, но дух тот же: `PostgresContainer`, `MinioContainer`, `ApiClient`, `db_engine`/`db_session` с savepoint-изоляцией — один набор фикстур вместо трёх копий одного и того же testcontainers-паттерна. Каждый сервис поднимает **свой** Postgres-контейнер через эти фикстуры — не общий контейнер с тремя БД; согласуется с CI-матрицей ADR 0010, где сервисы тестируются независимыми джобами.

**`test_security.py` (decode_access_token) и `test_errors.py` (обработчики `RequestValidationError`/`IntegrityError`) следуют за кодом в `kernel-platform`.** У `kernel-platform` появляется собственный `tests/` — то, чего дерево ADR 0010 явно не оговаривало (только `services/*/tests/`), восполняется здесь: любой член workspace с реальной логикой получает тесты, а `kernel-platform` теперь несёт `TokenVerifier`/`RequestContextMiddleware`/`problem()` — не протоколы без тела. Testcontainers `kernel-platform` не нужен — тестируемая логика не трогает БД.

**Остальное — по владению домена, без структурной переделки:**

| Файл | Судьба |
|---|---|
| `test_auth_e2e.py`, `test_user_repository.py` | identity, как есть |
| `test_schemas.py` | делится: Product-схемы → catalog, User-схемы → identity |
| `test_storage.py` | catalog (S3Storage — только там) |
| `test_pagination.py` | остаётся в catalog. Курсор алгоритмически домен-независим, но подтверждённого второго потребителя (identity под keyset для `ListUsersQuery`) не существует — по admission-правилу ADR 0013 в kernel не попадает |
| `test_product_repository.py`/`test_product_e2e.py`/`test_product_image_e2e.py`/`test_product_pagination_e2e.py` | catalog, кроме описанных выше 46 (→ Ф6 E2E) и admin-fallback-тестов (→ локально с фейковым `TokenVerifier`) |
| `test_smoke.py` (health-check) | по одному в каждый сервис |
| `test_smoke.py` (изоляция транзакций через savepoint) | `libs/test-support` — проверяет саму фикстуру, не домен сервиса |

**`support` — не перенос, а новая работа.** Ни одного файла тестов не существует. Написание тестового покрытия для `support` — обычная задача реализации Фазы 5, не предмет этого решения: DoD Фазы 5 TD уже формулирует, что должно быть верно («пользователь видит только свои обращения, admin — все»), детальный набор тестов проектируется при написании кода.

**Регресс-бар.** Тест, утверждающий то же наблюдаемое поведение (тот же код ответа, тот же результат видимости, та же форма audit-записи), что и соответствующий старый тест, — регресса нет, даже если `app/` к моменту проверки уже не существует. Старые тесты в git-истории репозитория остаются читаемым источником правды о поведении, даже когда перестают быть исполняемым.

## Considered Options

- **Большинство тестов — локально в catalog с прямым сидом `OwnerReadModel`, один представительный сценарий — в Ф6 E2E** — предложено первым, отклонено пользователем в пользу полного переноса всех 46 в E2E: цена «медленнее и избыточно» принята сознательно ради того, чтобы поведение проверялось через реальный сквозной путь на каждом эндпоинте, а не выборочно.
- **Все 46 → E2E, Фаза 3 без отдельного покрытия видимости до Фазы 6** — отклонено при повторной проверке: прямо противоречит собственному DoD Фазы 3 TD («Unit-тесты на все ветки видимости»), оставляя фазу без покрытия ключевого инварианта на всём протяжении Фаз 3–5.
- **Сократить 46 тестов до 1–2 представительных, остальные ветки — регресс без покрытия** — отклонено: теряет покрытие admin-ветки и идемпотентности двойной деактивации, которые сейчас проверены явно.
- **Дублировать test-фикстуры по сервисам, без `libs/test-support`** — отклонено: тройное копирование одного и того же testcontainers-паттерна, которое `libs/test-support` устраняет почти бесплатно (не production-зависимость, admission-правило ADR 0013 буквально не запрещает).
- **`kernel-platform`-тесты остаются дублированными по сервисам, использующим kernel-platform** — отклонено: противоречит принципу «код тестируется там, где живёт», который и обосновал перенос `decode_access_token`/обработчиков ошибок в kernel-platform в первую очередь.
- **Общий Postgres-контейнер с тремя БД вместо контейнера на сервис** — отклонено: расходится с независимыми CI-джобами ADR 0010 и вводит межсервисную координацию тестового окружения там, где её сейчас нет вовсе.

## Consequences

- Фаза 4 (catalog: инфраструктура, API, S3, интеграция identity) наследует уже написанный в Фазе 3 набор unit/интеграционных тестов видимости — не пишет его заново, только расширяет при необходимости.
- Фаза 6 получает готовый, длинный список E2E-сценариев (все 46 вариаций), а не придумывает покрытие с нуля — цена, которую платит производительность CI на этой фазе (много медленных сквозных прогонов вместо малого числа), компенсируется полнотой доказательства.
- `libs/test-support` — четвёртый член workspace сверх `kernel-domain`/`kernel-platform`/трёх сервисов; правится Makefile (`pkg=test-support` не имеет смысла как отдельная цель — библиотека не запускается сама, только импортируется тестами) и, при необходимости, CI-матрица ADR 0010, чтобы линтить и типизировать этот пакет наравне с остальными.
- Тесты admin-fallback (ADR 0012) обязаны появиться в catalog с тестовым двойником `TokenVerifier` уже в Фазе 4 — до того, как реальный `IdentityClient` из kernel-platform будет собран, они не могут проверить ничего, кроме факта вызова с ожидаемыми аргументами.
- `support`'s тестовое покрытие — открытый объём работы Фазы 5, не зафиксированный этим решением количественно; риск, что реализация начнётся без TDD-дисциплины, которую остальные два сервиса унаследовали от монолита автоматически.
