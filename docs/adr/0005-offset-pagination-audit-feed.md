# 0005. Offset-пагинация для глобального audit-фида товаров, вместо cursor

`GET /products/audit` (админский фид всех `ProductAuditLog`) неограниченно растёт и нуждается в пагинации. В отличие от `Product` (см. ADR 0001), `ProductAuditLog` — неизменяемая запись: строки только вставляются через ORM-события (`app/audit.py`) и никогда не удаляются и не обновляются (см. ADR 0004, CONTEXT.md → «Audit-лог»). Проблема «дрейфа» страниц при hard-delete, из-за которой ADR 0001 отклонил `limit/offset` для списков товаров, здесь структурно не возникает. Выбрали `page_index`/`page_size` offset-пагинацию вместо keyset-курсора — она даёт дешёвый `total`/`total_pages`, которые курсор принципиально не предоставляет, а для admin-only фида это ценнее непрозрачности курсора.

## Considered Options

- **Keyset-курсор** (как для `Product`, ADR 0001) — переиспользовал бы уже существующий паттерн (`Cursor`, `encode_cursor`/`decode_cursor`) и не заводил бы второй стиль пагинации в сервисе. Отклонён: `total`/число страниц для admin-фида важнее единообразия, а курсор их сознательно не даёт (см. ADR 0001 → Consequences).

## Consequences

- В сервисе теперь два стиля пагинации: keyset-курсор для product-list-эндпоинтов (ADR 0001) и offset — для этого одного audit-фида. Осознанная асимметрия, а не недосмотр.
- Мягкая версия дрейфа всё же возможна: при сортировке `created_at DESC` (дефолт) и параллельной вставке новых audit-записей во время пролистывания вперёд элемент может сместиться с одной страницы на другую между запросами разных страниц. Приемлемо для admin-only фида без жёстких гарантий консистентности между запросами.
- `page_index`/`page_size` передаются открытым текстом в query, без непрозрачного base64-токена — сознательное упрощение, отличающее этот эндпоинт от курсорных.
