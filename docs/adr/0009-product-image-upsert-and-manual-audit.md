# 0009. Upsert картинки товара через `INSERT ... ON CONFLICT DO UPDATE`, стабильный S3-ключ, ручная запись в Audit-лог

Вызывающий код (клиент) при загрузке Картинки товара (см. `CONTEXT.md` → «Картинка товара») не обязан заранее знать, есть ли у Товара уже Картинка — она могла быть добавлена сидированием, заменена или никогда не загружаться. `POST /api/v2/products/{id}/image` обслуживает оба случая (создание и замену) одним вызовом: строка `ProductImage` создаётся или обновляется единственным SQL-запросом — `INSERT ... ON CONFLICT (product_id) DO UPDATE ... RETURNING`, а не последовательностью «прочитать → решить insert или update». Это решение тянет за собой два следствия, зафиксированных здесь же: схему S3-ключа и способ ведения Audit-лога для этих мутаций.

## S3-ключ: стабильный, без расширения формата

Ключ объекта в хранилище — `products/{product_id}/image`, без расширения файла в имени. Повторная загрузка тому же Товару (в любом допустимом формате — JPEG/PNG/WEBP) всегда перезаписывает один и тот же объект; корректный `Content-Type` отдаётся заголовком объекта в S3, а не выводится из ключа.

Единственный случай, когда ключ Картинки товара меняется — переход с общего seed-плейсхолдера (`seed/placeholder.jpg`, см. `app/db.py`) на собственный ключ Товара: у многих сидированных Товаров Картинка изначально указывает на один и тот же объект-заглушку. Наивное удаление «старого ключа» при первой настоящей загрузке удалило бы этот общий объект и сломало бы Картинку у всех остальных Товаров, которые всё ещё на него ссылаются. Поэтому объект с префиксом `seed/` (`SEED_KEY_PREFIX` в `app/db.py`) никогда не удаляется — ни при замене Картинки, ни при её удалении (`DELETE /api/v2/products/{id}/image`).

### Considered Options

- **Ключ с расширением формата** (`products/{id}/image.jpg`) — отклонено: смена формата при замене (jpg → png) меняла бы ключ у собственных, не-seed изображений тоже, требуя cleanup-логики и там, ради чисто косметической выгоды («красивое» имя объекта), которую разработчик хранилища не видит — объект и так отдаётся клиенту исключительно по собранной публичной ссылке (`build_public_url`, ADR 0008), не как файл с говорящим именем.
- **Случайный/версионированный ключ на каждую загрузку** (например, с UUID или timestamp в имени) — отклонено: превращает каждую замену в потенциально растущий набор орфанных объектов в хранилище без встроенного механизма их удаления; версионирование ссылки для cache-busting на стороне клиента уже решено отдельно, query-параметром `v=<updated_at>` (ADR 0008), а не частью ключа.

## Audit-лог: явная запись в обход ORM-событий

ADR 0004 фиксирует, что Audit-лог создаётся автоматически на уровне ORM (`@event.listens_for` в `app/audit.py`), а не явным вызовом в коде репозитория/роутера. Эти события навешаны на `Mapper`-уровень unit-of-work и срабатывают только для объектов, прошедших через ORM `Session`-флаш (`session.add`/`session.delete` + `commit`) — они не видят «сырые» Core-запросы (`session.execute(insert(...)...)`), даже выполненные через ту же сессию. Raw SQL upsert, выбранный для картинки товара специально ради единого запроса без чтения-и-ветвления, физически не может запустить такие события.

Поэтому `ProductRepository.upsert_product_image`/`delete_product_image` пишут запись `ProductAuditLog` явно, в том же репозиторном методе и в той же транзакции, что и сам upsert/delete — двумя новыми значениями `ProductAuditAction`: `IMAGE_UPDATED` (создание и замена — одно действие, поскольку сам upsert их не различает на уровне SQL) и `IMAGE_DELETED`. Это осознанное, документированное исключение из общего правила ADR 0004 для одного конкретного случая, а не отказ от правила в целом — мутации самого `Product` (`name`/`category`/`price`/`is_active` и т.д.) по-прежнему проходят через ORM-события без изменений.

### Considered Options

- **ORM-события для `ProductImage`** (по аналогии с `Product`) — отклонено: единственный физически надёжный способ гарантировать их срабатывание — вставлять/обновлять `ProductImage` через ORM `Session` (get-or-create с `session.add`), а не через `INSERT ... ON CONFLICT DO UPDATE`, что прямо противоречит цели свести операцию к одному SQL-запросу.
- **Без Audit-лога для Картинки вовсе** — отклонено: `ProductImage` — часть Товара, а не независимая сущность; отсутствие аудита у одной из его мутируемых частей было бы дырой в общей истории изменений Товара, которую сопровождающий не ожидает, глядя на `GET /products/{id}/audit`.

## Consequences

- `ProductAuditAction` получил `IMAGE_UPDATED`/`IMAGE_DELETED` — миграция `d45d8b8b8aba` добавляет оба значения в нативный Postgres ENUM `productauditaction` (`ALTER TYPE ... ADD VALUE`, без отката — тот же паттерн, что и у миграции `c59a99e08069` для `ACTIVATED`/`DEACTIVATED`).
- `S3Storage` получил `put_object` (безусловная перезапись — в отличие от `ensure_object_exists`, который пропускает уже существующий ключ и поэтому не подходит для замены картинки с неизменным ключом) и `delete_object` (толерантен к отсутствию объекта).
- Владелец-или-admin проверка (`ensure_owner_or_admin`), ранее приватная в `app/router/products.py`, вынесена в общий `app/router/product_visibility.py` — тот же прецедент, что и у ADR 0007 для проверки видимости, чтобы `/api/v2`-роутер картинки использовал ту же проверку прав, что и мутации Товара в `/api/v1`.
- Любой будущий раздел API, которому понадобится настоящий upsert одним запросом (а не read-then-branch), должен так же явно предусмотреть, что ORM-аудит (если он есть у затронутой таблицы) на raw SQL не сработает.
