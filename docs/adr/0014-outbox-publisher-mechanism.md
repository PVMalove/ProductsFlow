# 0014. Механизм Transactional Outbox Publisher

TD (§5.1, Фаза 2b) оставляет открытым способ пробуждения Outbox Publisher — «периодически (polling или `LISTEN/NOTIFY`)» — и не фиксирует схему блокировки строк, семантику `attempts` и полный состав столбцов `outbox_messages`. ADR 0012 уже установил жёсткое ограничение сверху: приемлемое окно рассинхронизации между записью события и его применением в read-модели — секунды. Находки по `aio-pika` (issue #64) установили факт, который сужает пространство решений: порядок доставки в RabbitMQ не гарантирован даже для одного консьюмера.

**Механизм пробуждения — гибрид.** `LISTEN/NOTIFY` даёт почти мгновенную реакцию в счастливом пути; фоновый polling раз в 5 секунд — страховку от фундаментальной ловушки Postgres-уведомлений: `NOTIFY` fire-and-forget, и если воркер в момент отправки не слушает (рестарт, разрыв соединения к БД), уведомление теряется безвозвратно, а не встаёт в очередь. 5 секунд — с запасом внутри окна ADR 0012 и не создаёт заметной нагрузки на Postgres при опросе `WHERE published_at IS NULL AND next_attempt_at <= now()`.

**Блокировка строк.** Один экземпляр воркера на сервис в Фазах 0–6 — TD не масштабирует воркеры в таблице compose (`--scale` относится только к `*-api`, Фаза 7), и у витрины без реальной нагрузки нет причины вводить конкурентных воркеров сейчас. Запрос тем не менее пишется через `SELECT ... FOR UPDATE SKIP LOCKED` — это естественный способ написать такой запрос в Postgres, стоит почти ничего, и оставляет дверь к горизонтальному масштабированию воркера открытой без переделки кода, если она когда-нибудь понадобится.

**`attempts` — только backoff, без give-up.** Publisher никогда не сдаётся: отказ от повторной отправки после исчерпания счётчика ломает саму гарантию At-Least-Once, ради которой Outbox вводится. Перечитанный DoD Фазы 2b подтверждает это разделение ответственности: тест (в) («отравленное» сообщение уходит в DLQ после исчерпания retry) стоит в одном списке с тестом (б) (двойная доставка `message_id` не создаёт дублей) — оба про поведение consumer'а, не publisher'а. DLQ для непроходимого payload — предмет топологии RabbitMQ (issue #67), не этого решения. `attempts` инкрементируется на каждую неудачную попытку и определяет экспоненциальный backoff с потолком; `next_attempt_at` — производная колонка, чтобы фоновый poll не перебирал строки, которым рано повторяться.

**Порядок для read-моделей (вход для issue #71).** Глобальный `id` (`bigserial`) уже монотонен по построению и уже есть в схеме TD. identity — единственный писатель `outbox_messages`, воркер — один экземпляр, поэтому порядок вставки совпадает с порядком `id` без дополнительных гарантий. Фильтр по `aggregate_type = 'User'` (и добавленному `aggregate_id`, см. ниже) даёт issue #71 готовый тотальный порядок событий одного агрегата бесплатно, без отдельного счётчика версии на самом агрегате.

**Итоговая схема `outbox_messages`** (TD называет `id, aggregate_type, event_type, payload, occurred_at, published_at, attempts` — ниже дополнено тем, что требуют принятые здесь решения):

| Столбец | Тип | Зачем |
|---|---|---|
| `id` | `bigserial` PK | Порядок доставки; используется как порядок агрегата (issue #71) |
| `aggregate_type` | `text` | Из TD |
| `aggregate_id` | `bigint` | **Добавлено.** Без него порядок по агрегату (issue #71) требовал бы разбора `payload`; с ним — обычный индексированный фильтр |
| `event_type` | `text` | Из TD |
| `payload` | `jsonb` | Из TD |
| `occurred_at` | `timestamptz` | Из TD |
| `published_at` | `timestamptz`, nullable | Из TD; частичный индекс `WHERE published_at IS NULL` под poll-запрос |
| `attempts` | `int`, default 0 | Из TD; для backoff, не для give-up |
| `next_attempt_at` | `timestamptz`, nullable | **Добавлено.** Следствие backoff без give-up — без этого столбца poll-запрос не может пропустить строки, которым рано повторяться |
| `trace_context` | `text` | **Добавлено.** Зафиксировано находками #64: OTel инъектит `traceparent` в момент `publish`, уже в воркере — без переноса контекста трейс рвётся на шине уже в Фазе 2b, хотя сам трейсинг реализуется в Фазе 10 |

**`published_at` относительно publisher confirms.** Проставляется только после `isinstance(result, Basic.Ack)` — находки #64 показали, что `on_return_raises=False` (дефолт `aio-pika`) молча возвращает `ReturnedMessage` вместо исключения при отсутствии биндинга, и это единственная надёжная проверка. `ReturnedMessage` (сообщение не доставлено ни одной очереди) — это структурная ошибка топологии (issue #67), а не транзиентный сбой: ретраить её бессмысленно, строка логируется как аномалия наравне с фактическим отказом брокера.

## Considered Options

- **Только polling** — просто и ничего не пропускает по конструкции. Отклонено: даже щедрый интервал в несколько секунд ближе к верхней границе ADR 0012, чем гибрид, без причины отказываться от почти мгновенной реакции NOTIFY там, где она работает.
- **Только `LISTEN/NOTIFY`, без страховки** — минимальная задержка в норме. Отклонено: пропущенное уведомление зависает в очереди без срока — только следующее NOTIFY случайно её вытолкнет. Нарушает окно ADR 0012 в любой сценарий рестарта воркера, который неизбежен при каждом деплое.
- **Advisory lock на весь воркер вместо `SKIP LOCKED` на строки** — проще для одного экземпляра. Отклонено: при будущем масштабировании воркера один advisory lock блокирует всю таблицу целиком, вторая реплика простаивает вместо того, чтобы делить работу — тогда как `SKIP LOCKED` даёт это бесплатно уже сейчас.
- **Строго один экземпляр воркера без блокировки строк вовсе** — дешевле всего написать. Отклонено: закрывает дверь к горизонтальному масштабированию воркера без переписывания запроса, а `SKIP LOCKED` стоит той же одной строки кода.
- **Публикатор тоже сдаётся после N попыток** — читается как прямое прочтение столбца `attempts` в схеме TD. Отклонено при перечитывании DoD: give-up на стороне publisher — это тихая потеря события, обратное тому, ради чего Transactional Outbox вводится (§5.1 явно называет цель — «потеря невозможна, ценой возможных дублей»). DLQ из DoD относится к consumer-стороне.
- **Отдельный счётчик `aggregate_version` на самом агрегате `User`** — более явный и переносимый сигнал порядка, не завязанный на детали реализации outbox-таблицы. Отклонено как избыточное для issue #71: требует атомарного инкремента счётчика в той же транзакции, что и мутация агрегата, ради гарантии, которую глобальный `id` уже даёт бесплатно при единственном писателе и единственном воркере.
- **`occurred_at` как сигнал порядка** — не требует новых столбцов вовсе. Отклонено: `timestamptz` даёт более слабую гарантию, чем монотонный `id`, при двух событиях, зафиксированных в одной транзакции (одинаковый `occurred_at`, неопределённый порядок).

## Consequences

- Схема `outbox_messages` дополняет TD двумя новыми столбцами (`aggregate_id`, `next_attempt_at`) и одним, ранее отмеченным находками #64 (`trace_context`), сверх пяти исходных. Расхождение с буквальным текстом TD осознанное и обосновано выше.
- Порядок для read-моделей (issue #71) закрыт побочно: `outbox_messages.id`, отфильтрованный по `aggregate_type`/`aggregate_id`, — готовый тотальный порядок без отдельного решения по версионированию агрегата. Issue #71 остаётся открытым в части того, как именно read-модель **использует** этот порядок (сравнение при апдейте, разрешение конфликта с синхронным добором из ADR 0012), но не в части того, откуда берётся сам порядковый номер.
- Гарантия монотонности `id`-как-порядка опирается на «один воркер, один писатель». Если Фаза 7 когда-нибудь масштабирует Outbox-воркер горизонтально, это предположение придётся пересмотреть явно — сейчас оно не переносится по построению, а фиксируется как условие, а не забывается.
- Publisher, который никогда не сдаётся, при постоянно недоступном брокере копит растущий backlog `outbox_messages` без верхней границы. Это осознанный компромисс: альтернатива (give-up) означает тихую потерю события. Наблюдаемость этого backlog (лаг публикации, возраст самой старой неопубликованной строки) — предмет Фазы 9, за границей destination; здесь фиксируется только то, что метрика должна на что-то опираться, когда появится.
- `ReturnedMessage` как структурная, а не транзиентная ошибка предполагает существующую топологию (exchange/биндинги) к моменту первой публикации — реализация Outbox Publisher по времени зависит от результата issue #67, хотя это решение от него не блокируется.
