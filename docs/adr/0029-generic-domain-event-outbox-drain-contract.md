# 0029. Общий контракт DomainEvent и generic drain-в-outbox в kernel-platform

ADR 0021 сознательно оставило маппинг «доменное событие → строка `outbox_messages`» локальным `ProductRepository` в catalog-service: на тот момент identity-service ещё не писал `User` в персистентность вовсе, второго подтверждённого потребителя не было, а admission-правило ADR 0013 требует минимум двух. Epic #198 (`identity-service: полная реализация`, TD-01 Фаза 2) меняет это: он прямо решает, что `identity-service` реализует тот же паттерн для `User` тем же усилием, каким `kernel-platform` получает общий контракт — то есть подтверждение второго потребителя дано самим принятым решением epic'а, ровно как ADR 0013 допускает («подтверждение даёт либо принятый ADR/решение TD, либо факт использования в коде»). Issue #199 — первый из трёх последовательных PR epic'а — выполняет обобщение и мигрирует единственного уже существующего потребителя (`catalog-service`/`Product`); `identity-service`/`User` подключается к тому же контракту отдельным PR (issue #201).

Помимо `Product` в catalog-service, тот же ручной паттерн «репозиторий сам мапит событие в `OutboxMessage`» независимо завёлся и в `support-service` (`SqlTicketRepository`, issue #196) уже после ADR 0021. Он не переводится на общий контракт в рамках этой задачи — issue #199 ограничен `catalog-service` (см. Acceptance Criteria issue #199); миграция `support-service` — самостоятельное решение за пределами этого ADR, если/когда она понадобится.

**Решение.** `kernel_domain.domain_event.DomainEvent` получает контракт из двух `ClassVar`-полей (`event_type: str`, `aggregate_type: str`) и двух методов (`aggregate_id() -> uuid.UUID`, `to_payload() -> dict[str, Any]`), каждый — `raise NotImplementedError` в базовом классе. Поля объявлены как `ClassVar`, а не как обычные dataclass-поля: `event_type`/`aggregate_type` — свойства класса события (одно значение на весь класс, не за экземпляр), в отличие от `id`/`occurred_on_utc`, которые действительно различаются между экземплярами. Существующие специфичные для события поля (`ProductEvent.product_id`) не переименовываются и не убираются — `aggregate_id()`/`to_payload()` читают их и строят генерическое представление поверх, не заменяя их.

`kernel_platform.outbox.drain.drain_events_to_outbox(session, entity)` — новая generic-операция: вызывает `entity.pull_events()` и для каждого `DomainEvent` строит `OutboxMessage(aggregate_type=event.aggregate_type, aggregate_id=event.aggregate_id(), event_type=event.event_type, payload=event.to_payload(), occurred_at=event.occurred_on_utc)`, добавляя его в переданную сессию (без коммита — транзакция остаётся за вызывающим репозиторием, как и раньше). Функция ничего не знает ни о `Product`, ни о `User` — она полностью управляется контрактом `DomainEvent`. Это делает `kernel_platform` новым зависимым от `kernel_domain` path-пакетом (в `pyproject.toml` `kernel-platform` появляется `kernel-domain` как `[tool.uv.sources]`-зависимость) — раньше `kernel_platform`/src не импортировал `kernel_domain` вовсе; направление зависимости (`kernel-platform` → `kernel-domain`, не наоборот) не противоречит ADR 0013: `kernel-domain` остаётся без единой внешней зависимости, `kernel-platform` как более высокий слой имеет право знать о доменном контракте.

`ProductRepository` (catalog-service) больше не содержит `_to_outbox_message`/`_EVENT_TYPES` — оба мутирующих пути (`_commit`, `delete`) вызывают `drain_events_to_outbox(self.session, product)`. Пять подклассов `ProductEvent` реализуют контракт: `ProductEvent` (общий предок) задаёт `aggregate_type = "Product"` и реализует `aggregate_id()`/базовый `to_payload()` (`{"product_id": ...}`), `ProductCreated` переопределяет `to_payload()`, расширяя базовый через `super()`, остальные четыре только объявляют свой `event_type`.

## Considered Options

- **`aggregate_id` как обычное dataclass-поле на `DomainEvent`, параллельно уже существующему `product_id`** — отклонено: требовало бы либо дублировать один и тот же UUID в двух полях на каждом вызове конструктора события (`ProductCreated(product_id=id, aggregate_id=id.value, ...)`), либо переименовать/убрать `product_id` — оба варианта прямо запрещены Acceptance Criteria issue #199. Метод, вычисляющий `aggregate_id()` из уже существующего поля, даёт то же самое без дублирования и без изменения существующих полей.
- **Единый метод `to_outbox_message()` на `DomainEvent`, возвращающий готовый `OutboxMessage`** — отклонено: заставил бы `kernel-domain` (по ADR 0013 — только stdlib, без единой внешней зависимости) знать о SQLAlchemy-модели `OutboxMessage` из `kernel-platform`, переворачивая направление зависимости, которое ADR 0013 закрепил. Разделение на `aggregate_id()`/`to_payload()` (простые Python-типы) и генерическую сборку `OutboxMessage` в `kernel-platform` держит `kernel-domain` чистым.
- **Мигрировать заодно и `support-service`/`SqlTicketRepository` на общий контракт** — отклонено для этой задачи: issue #199 явно ограничен `catalog-service` в Acceptance Criteria; расширение на `support-service` не была ни запрошена, ни протестирована в рамках этого PR — самостоятельное решение позже, тем же admission-принципом (третий факт использования уже есть, четвёртый не нужен).
- **Оставить маппинг локальным `ProductRepository`, дождаться, пока `identity-service` реально начнёт писать `User` в персистентность (issue #201), и обобщать только тогда** — отклонено: сам epic #198 уже фиксирует решение обобщать вместе с этой миграцией, откладывать это ADR до #201 создало бы противоречие между уже принятым решением epic'а и ещё не обобщённым кодом ровно на один PR дольше без причины.

## Consequences

- `kernel-platform`/`pyproject.toml` получает новую path-зависимость на `kernel-domain` — первая для этого пакета; `kernel-domain` остаётся без единой внешней зависимости (ADR 0013 не нарушен, только использован в новом направлении).
- Любой будущий потребитель transactional outbox (identity-service/`User` — issue #201; гипотетически support-service/`Ticket` позже) подключается, только реализовав `DomainEvent`-контракт на своих событиях и вызвав `drain_events_to_outbox` — без нового кода в `kernel-platform` и без ручного маппинга в своём репозитории.
- `catalog-service`-тесты (юнит и интеграционные, включая репозиторий и outbox) остаются зелёными без изменения ожидаемого поведения — рефактор поведенчески нейтрален, что было явным условием Acceptance Criteria issue #199.
- `support-service`/`SqlTicketRepository` продолжает собственный ручной маппинг — не регрессия, осознанно оставлено вне рамок этого решения (см. выше).
