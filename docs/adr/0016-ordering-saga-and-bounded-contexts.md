# 0016. Ordering: отдельные контексты и оркестрируемая Saga checkout

**Статус:** Accepted

`order-service` владеет серверной `Cart` и `Order`; `inventory-service` владеет доступным остатком и `Inventory Reservation` с TTL 15 минут; `payment-service` владеет `Payment Authorization` и `Capture`. Перед checkout `order-service` синхронно получает у `catalog-service` авторитетный `Checkout Quote` и фиксирует из него коммерческий снимок — клиентской цене не доверяет. Оформление заказа — длительная распределённая транзакция, управляемая persistable state machine в `order-service`: `quote` → `Pending Order` → резервирование строк → авторизация суммы подтверждённых строк → обратимое `Allocation` → capture. `order-service` публикует адресованные RabbitMQ-команды и ждёт коррелированные события-результаты; состояние Saga хранится в его БД. При неуспехе оркестратор выполняет компенсирующие действия — освобождает allocation/резерв и отменяет авторизацию — вместо 2PC или некоординируемой хореографии.

Внешний `Order Status` (`PENDING`, `COMPLETED`, `CANCELLED`, `EXPIRED`, `FAILED`) не раскрывает внутренний `Saga Step`. Обработка сообщений имеет at-least-once семантику: каждый участник идемпотентно принимает `command_id`/`causation_id` через inbox/`processed_messages`, а переход автомата и исходящее сообщение пишутся с outbox в одной локальной транзакции. Неизвестный результат capture переводит Saga в `PENDING_RECONCILIATION`; повторять capture до сверки результата у `payment-service` по идемпотентному ключу запрещено.

Первая версия — demo: `Money` выражается целыми копейками RUB, цена Catalog уже включает налог, а доставка, промокоды и самостоятельный расчёт налогов не входят в scope. Заказать можно только активные физические товары в положительном целом количестве; backorder и дробные/цифровые товары исключены. `COMPLETED` означает «оплачен и выделен для будущего fulfillment»: `order-service` публикует `order.completed.v1`, но не владеет отгрузкой или доставкой. `payment-service` интегрируется только с детерминированным Test PSP, без реального провайдера и реального перевода средств.

Checkout атомарно фиксирует versioned `Checkout Selection`; изменять вошедшие в неё Cart Line до терминального результата Saga нельзя. Недоступный Catalog при запросе quote не создаёт Order и возвращает временную ошибку `CATALOG_UNAVAILABLE`. Для `checkout` и отмены `order-service` локально проверяет подпись JWT через JWKS и синхронно сверяет активность пользователя в `identity-service`; недоступность identity приводит к fail-closed `503`.

RabbitMQ разделён на durable topic exchanges: `productsflow.commands` содержит адресные versioned-команды Saga (`inventory.*.v1`, `payment.*.v1`) с одной очередью-владельцем, `productsflow.events` — versioned факты. Watchdog даёт до трёх минут на ответ каждого шага и запускает компенсацию по дедлайну. Для transient-ошибок применяется retry-лестница 5с → 30с → 2мин, после которой сообщение попадает в per-service DLQ с метрикой/alert и допускает ручной replay после устранения причины. После терминального результата `order-service` публикует `order.completed.v1`, `order.failed.v1`, `order.cancelled.v1` либо `order.expired.v1` с данными, разрешёнными политикой анонимизации.

Покупатель управляет только своей Cart, запускает checkout, читает/листает только собственные Order и отменяет только `PENDING`; admin имеет read-only поиск и просмотр. `order-service` сохраняет неизменяемую техническую историю переходов Saga и попыток команд с correlation/causation/trace IDs, но раскрывает покупателю только статус и допустимые причины. При `user.deleted.v1` `customer_id` в Order становится `NULL`, записывается `anonymized_at`; имя, email, адрес и иной PII не хранятся, а внешние события не содержат идентификатора пользователя. Адреса, контакты и доставка принадлежат будущему fulfillment-контексту, не `order-service`.

Test PSP детерминированно принимает тестовые payment method/token сценарии `success`, `decline`, `timeout`, `unknown_capture` только в demo/test-конфигурации и сохраняет операцию по idempotency key для проверки reconciliation. Inventory подписывается на жизненный цикл Product и создаёт для нового товара нулевой Available Stock; admin изменяет остаток только отдельными аудитируемыми командами/API, а demo явно сидирует данные. Catalog не владеет количеством. В v1 один `Inventory Pool` на продукт. `Checkout Quote` возвращает `discount_amount = 0`, а Catalog остаётся источником unit price; поля скидки сохранены в коммерческом снимке для будущей pricing-модели.

При `FAILED`, `EXPIRED` или `CANCELLED` до capture исходные Order Line после успешной компенсации возвращаются в Cart с причиной результата, а сам Order остаётся в истории. Деактивация или удаление Product после quote не отменяет уже созданные snapshot и reservation: они завершаются по зафиксированным данным; lifecycle-событие лишь прекращает новые quote и резервирование этого товара. Аудитируемая Stock Adjustment не может уменьшить физический остаток ниже действующих reservation/allocation и никогда не делает `available_stock` отрицательным. Если результат capture остаётся неизвестным, Saga остаётся `PENDING_RECONCILIATION`/`PENDING`: автоматическая компенсация запрещена до достоверной сверки, а технический журнал даёт admin возможность устранить причину и повторно доставить сообщение.

## Consequences

- У каждого из трёх новых сервисов собственная БД; доступ к данным других контекстов только через явно определённые контракты интеграции.
- Каждый новый сервис следует общему канону [ADR 0006](0006-service-internal-architecture-baseline.md): Hexagonal Architecture, Always-Valid Domain, локальный CQRS, domain-порты, явный Unit of Work, transactional outbox и проверяемое направление зависимостей `api → application → domain`.
- `Order` остаётся источником статуса процесса для клиента, а не выводится из состояния корзины, склада или платёжного провайдера.
- Нехватка части позиций не является провалом всей Saga: подтверждённый `Order` включает только строки, для которых получен резерв; недоступные `Cart Line` не становятся `Order Line`.
- Если не удалось зарезервировать ни одной строки, Order завершается с `Order Status=FAILED` и причиной `NO_ITEMS_AVAILABLE`; Cart сохраняется без изменений.
- При истечении резерва `inventory-service` его освобождает и уведомляет `order-service`; тот завершает незавершённый Order терминальным состоянием. При удалении пользователя Order сохраняется анонимизированным.
- Успешно зарезервированные строки удаляются из `Cart`, недоступные остаются в ней с причиной. До `Capture` пользователь может отменить `Pending Order`; это запускает отмену авторизации и освобождение резерва. Возвраты после capture не входят в первую версию.
- Каждый шаг имеет дедлайн: при таймауте начинается компенсация; опоздавший успешный результат не возобновляет Saga, а вызывает свою компенсацию. `user.deleted` отменяет `PENDING` Order с компенсацией, `COMPLETED` Order сохраняет анонимизированным.
- API checkout требует уникальный в рамках пользователя `Idempotency-Key`: повтор с тем же телом возвращает тот же Order, с другим телом — ошибка конфликта.
- Конкретные состояния, контракты команд/событий, идемпотентность, дедлайны и правила для сбоев определяются до реализации, потому что от них зависит корректность компенсаций.
