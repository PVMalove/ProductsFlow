# 0013. Стратегия тестирования: пирамида, E2E через Gateway, изоляция окружения и данных

**Статус:** Accepted

## Три уровня, разные вопросы

- **Unit** (`tests/unit/`) — доменная логика и политика видимости изолированно: без БД, без брокера, без сети. Read-модели (`OwnerReadModel`, `user_projection`) сеются напрямую в тестовую БД, не через событие. Синхронный fallback catalog ([ADR 0011](0011-catalog-service-event-integration.md)) тестируется локально фейковым `TokenVerifier`/`IdentityClient` — тестовым двойником, без реального identity и без RabbitMQ.
- **Integration** (`tests/integration/`) — репозиторий/persistence/outbox-механика одного сервиса на реальном Postgres (testcontainers) и, где применимо, MinIO — в границах одного сервиса.
- **E2E** (`backend/tests/e2e/`, session-scoped фикстура) — сквозной путь через реальный identity + RabbitMQ + все три сервиса, доказывающий, что событие реально доставляет то состояние, которое политика видимости ожидает.

`libs/test-support` — dev-only библиотека с общими `PostgresContainer`, `MinioContainer`, `ApiClient`, `db_engine`/`db_session` (savepoint-изоляция), `FakeUnitOfWork` ([ADR 0006](0006-service-internal-architecture-baseline.md)). Каждый сервис поднимает **свой** Postgres-контейнер, не общий контейнер с тремя БД — согласуется с независимыми CI-джобами на пакет.

## E2E: black-box через Gateway, изолированное окружение

E2E-тесты обращаются к системе исключительно через E2E-only Nginx Gateway ([ADR 0004](0004-api-gateway-and-routing.md)) по неизменённым публичным BFF-путям — не напрямую к сервисам, БД или брокеру.

**Изолированный стек на каждый прогон, без фиксированных имён.** Session-scoped `pytest_asyncio.fixture` поднимает `docker compose --project-name productsflow-e2e` (`docker-compose.yml` + `docker-compose.e2e.yml`) с портом Gateway, выбранным динамически (`_free_tcp_port()` — свободный порт `127.0.0.1`, не захардкоженный). Отдельный project name (не фиксированные `container_name`, [ADR 0004](0004-api-gateway-and-routing.md)) даёт стеку собственное пространство имён контейнеров и volumes — параллельный dev-стек не конфликтует. Стек поднимается `up --build --detach --wait` и уничтожается `down -v --remove-orphans` в `finally` фикстуры независимо от исхода тестов.

## Readiness: строгий поллинг с джиттером, fail-fast на неожиданном статусе

Готовность стека — не фиксированная пауза, а активный поллинг конкретных HTTP-условий через Gateway, с экспоненциальной задержкой и джиттером против synchronized retry (`thundering herd` нескольких проверок одновременно):

- Задержка между попытками растёт от `0.1s` до потолка `2.0s` (`delay = min(MAX, delay * 2)`), каждая конкретная пауза — само значение, умноженное на случайный коэффициент `uniform(0.8, 1.2)` (джиттер), не голое удвоение.
- Общий дедлайн — `30s`; по истечении тест падает с последним телом ответа в сообщении, не зависает.
- **Опрашиваются только явно перечисленные транзиентные исходы** (`retry_statuses`) — любой другой код ответа или неожиданная ошибка запроса **сразу проваливает тест** (`pytest.fail`), не уходит в очередной виток поллинга. Это — сознательное отличие от «ретраить всё подряд, пока не истечёт таймаут»: тест обязан быстро упасть на структурной ошибке (например, `500` в раннем ответе сервиса) и медленно ждать только там, где ожидание оправдано (сервис ещё не готов, событие ещё не доставлено).

Последовательность готовности перед прогоном тестов: `GET /.well-known/jwks.json` → `200` (identity поднялся и опубликовал JWKS) → логин сидированного admin → `GET /api/v1/tickets` с `retry_statuses=(401,)` — `401` здесь не ошибка авторизации, а сигнал, что асинхронная `user_projection` support ([ADR 0012](0012-support-service-event-integration.md)) ещё не применила `user.registered.v1` сидированного admin; тест ждёт именно эту конкретную, заранее объяснимую переходную форму отказа, а не любую.

Тот же паттерн (строгий поллинг тела ответа, не статус-кода) используется, где транзиентный сигнал живёт не в HTTP-статусе, а в бизнес-состоянии ответа — например, ожидание, пока асинхронный consumer support закроет тикет после удаления его автора: опрашивается `200`-ответ до тех пор, пока `data.status` не станет терминальным; любой не-`200` или ошибка запроса завершает тест немедленно.

## Изоляция данных: уникальные суффиксы, не очистка БД

Каждый тестовый сценарий создаёт собственные, гарантированно уникальные данные вместо того, чтобы полагаться на очистку общей БД между тестами. Идентификатор — `uuid.uuid4().hex`, генерируемый в начале сценария и используемый как суффикс email/имени: `f"e2e-owner-{suffix}@example.test"`, `f"E2E product {suffix}"`. Пользователи создаются самостоятельной регистрацией через тот же публичный API, не сидированием в обход бизнес-правил. Это делает тесты независимыми от порядка выполнения и от состояния БД, накопленного предыдущими прогонами — параллельный запуск и повторный прогон без сброса volume безопасны без privileged cleanup-эндпоинта.

## Регресс-бар

Тест, утверждающий то же наблюдаемое поведение (тот же код ответа, тот же результат видимости, та же форма audit-записи), что и любой предшествующий тест того же инварианта, — регресса нет, даже если тест, который он заменяет, уже удалён.

## Considered Options

- **Фиксированный порт Gateway в E2E-конфигурации** — отклонено: конфликтует при параллельном запуске нескольких E2E-прогонов на одной машине/CI-раннере; динамический свободный порт снимает координацию совсем.
- **Очистка БД между тестами (truncate/rollback общей транзакции)** — отклонено для E2E: сценарии идут через реальные HTTP-запросы к трём независимым сервисам и брокер, общая транзакция недостижима технически; UUID-суффиксы дают эквивалентную изоляцию без инфраструктуры сброса состояния.
- **Слепой retry на любой код ответа до истечения таймаута** — отклонено: маскирует структурные ошибки (например, `500` из-за реальной поломки) под «сервис ещё не готов», превращая быстрый и информативный отказ в 30-секундное ожидание с непонятной причиной.
- **Фиксированная (без джиттера) экспоненциальная задержка** — отклонено: при нескольких параллельных проверок готовности синхронизированные попытки создают пики нагрузки на ещё не полностью прогревшийся стек; джиттер их размазывает.

## Consequences

- Новый бизнес-инвариант, затрагивающий видимость по read-модели, по умолчанию получает и unit-покрытие политики, и E2E-сценарий через Gateway — не одно вместо другого.
- Любой новый E2E-сценарий обязан порождать собственные уникальные тестовые сущности (UUID-суффикс) и использовать `_wait_for_response`-паттерн (явный список ожидаемых транзиентных статусов, fail-fast на прочих) — произвольный `sleep()`/безусловный retry не проходит ревью.
- `support-service`'s тестовое покрытие строится с нуля по тем же правилам, что и у identity/catalog — в проекте нет прецедента «более лёгкого» стандарта тестирования для более позднего по времени реализации сервиса.
