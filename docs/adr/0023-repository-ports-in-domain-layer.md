# 0023. Репозитории: порт в domain-слое, реализация в infrastructure

> **Superseded решением [ADR 0025](0025-application-layer-ports-and-local-cqrs.md).**
> Исторический текст ниже сохранён без переписывания: repository и gateway
> порты принадлежат application-слою — потребителю use case, а не domain-модели.

`identity-service` уже завёл `UserRepository` как `Protocol` (issue #140/#143) — но в `identity/application/user_repository.py`, не в `domain/`. `catalog-service` (#148/#149) не завёл абстракции вовсе: `ProductRepository` — конкретный SQLAlchemy-класс в `catalog/infrastructure/db/product_repository.py`, и HTTP-роутер (`catalog/api/products.py`) конструирует и вызывает именно его, напрямую. В обоих случаях application/presentation-код видит либо порт, лежащий не на своём месте, либо саму инфраструктуру — то есть зависимость идёт от «правил» (domain) к «деталям» (SQLAlchemy), а не наоборот, что и есть нарушение инверсии зависимостей (DIP), которую распил на микросервисы призван соблюдать.

**Решение.** Контракт персистентности агрегата — часть его bounded context, то есть domain-слоя, а не application: то, *как* сохраняется `User`/`Product`, определяет сам домен, а application (обработчики команд/запросов, #157/#158) — только потребитель этого контракта. Отсюда:

- Протокол репозитория живёт в `<service>/domain/repositories.py` (один файл на сервис — сейчас у каждого сервиса ровно один агрегат с персистентностью; второй файл заводится, когда появится второй агрегат, а не заранее).
- Конкретная реализация (SQLAlchemy, in-memory фейк для тестов) — исключительно в `infrastructure/` (продакшен) или `tests/` (тестовые дублёры) — никогда в `domain/`.
- `application/`-слой (хендлеры команд/запросов) импортирует только доменный `Protocol` для тайп-хинтов; конкретная реализация подставляется через DI на границе: `Depends()`-фабрику в catalog (уже есть механизм — `DbSessionDI`/`IdentityGatewayDI` в `catalog/infrastructure/security/auth.py`, тот же приём распространяется на репозиторий), явную инъекцию через конструктор в identity (там пока нет HTTP-слоя — композиция происходит в тестах/будущем составном корне).

## Considered Options

- **Оставить порт там, где он сейчас** (рядом с единственным текущим потребителем, то есть в `application/`, как уже сделано в identity) — отклонено: это не решает DIP, а маскирует его — `application` в этой раскладке становится тем же «случайным владельцем» абстракции, что и `domain`, только произвольно выбранным по факту первого использования. DDD относит контракт персистентности агрегата к его собственному bounded context.
- **Не заводить абстракцию для catalog вовсе** (статус-кво, роутер зовёт `ProductRepository` напрямую) — отклонено: тот же архитектурный пробел, который уже признан ошибкой в identity (порт хотя бы существует, просто не на своём месте) — здесь нет и порта. Несогласованность между двумя сервисами усложняет обоснование конвенции в #157/#158 (CQRS-хендлеры не могут единообразно зависеть «только от domain», если у catalog domain нечего предложить).
- **Generic `Repository[TAggregate, TId]` в kernel_domain** — отклонено на тех же основаниях, на которых issue #63 (`docs/tasks/issue-59-microservices-migration/issue-63-findings-founder-testtask.md`, §2.1/§8.2) уже отклонил `IDefaultRepository<T>` из `Founder.TestTask`: там абстракция протекала (`Where() → IQueryable`, EF Core просачивался в Application-слой), а полезная работа всё равно оседала в именованном репозитории агрегата. У каждого сервиса свои методы (`get_by_email`, keyset-пагинация `list`) — общего интерфейса, покрывающего оба без утечки или урезания, не существует. Admission-правило kernel (ADR 0013: «минимум два подтверждённых потребителя с реальным перекрытием») здесь тоже не выполнено.

## Consequences

- `identity/application/user_repository.py` перестаёт существовать — контракт переезжает в `identity/domain/repositories.py`; `identity/application/{register_user,login,change_password,deactivate_user}.py` и `tests/unit/fake_user_repository.py` меняют путь импорта (issue-заявка на эту миграцию — отдельный тикет, блокирующий #157, чтобы #157 не переписывал одни и те же импорты дважды).
- `catalog-service` получает `catalog/domain/repositories.py` с `Protocol ProductRepository`, зеркалящим публичную поверхность уже существующего `catalog.infrastructure.db.product_repository.ProductRepository` (create/get_by_id/update/activate/deactivate/delete/list). Существующий конкретный класс остаётся единственной реализацией; вопрос об именовании (оставить как есть — Python допускает одинаковое имя протокола и реализации в разных модулях — или дать реализации суффикс) решается на уровне issue, не этой ADR.
- `catalog/api/products.py` перестаёт импортировать конкретный `catalog.infrastructure.db.product_repository.ProductRepository` напрямую — получает его через `Depends()`-фабрику, типизированную доменным `Protocol`.
- **Не затронуто этой ADR** (сознательно, чтобы не расширять решение сверх заявленного):
  - `owner_read_model` (catalog) — это CQRS read-side проекция, читаемая query-хендлерами напрямую, не порт персистентности агрегата. Проведение через тот же `Protocol`-паттерн было бы абстракцией ради абстракции (karpathy-guidelines §2) — read-модель и так уже отделена от `Product`-агрегата по конструкции (ADR 0019).
  - `catalog.infrastructure.identity_gateway.IdentityGateway` — структурно тот же DIP-вопрос (порт для внешнего bounded context, identity-service), но уже сейчас `Protocol`, просто в `infrastructure/`, а не в `domain/`. Не входит в эту ADR, потому что запрос был явно ограничен репозиториями — открытый вопрос для будущей сессии.
  - `identity.application.password_hasher.PasswordHasher` — тот же непорядок расположения (`application/`, не `domain/`), что был у `UserRepository`, но это не порт персистентности агрегата, а стейтлес-сервис (хеширование) — относится ли он к domain-слою по тем же основаниям, вопрос отдельный и здесь не решается.
