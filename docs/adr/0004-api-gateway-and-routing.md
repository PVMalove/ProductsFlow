# 0004. Роутинг: единая версия API и Nginx Gateway (dev/prod + отдельный E2E)

**Статус:** Accepted

## Единая версия API — без `/api/v1`/`/api/v2`

Ни один из трёх сервисов не разводит версии API. Все бизнесовые эндпоинты живут под одним `/api/v1`; второй версии нет ни у одного сервиса — все три создавались с нуля, без унаследованных клиентов и выпущенных контрактов, которые нужно было бы защищать разведением версий. Если у какого-либо сервиса появится реальная причина не ломать уже выпущенный `/api/v1` (внешние клиенты и т. п.), решение о второй версии принимается заново, с этим новым основанием, а не превентивно.

## Nginx Gateway — единая точка входа для dev/prod, отдельно от E2E

Топология с единой точкой входа для клиентского трафика зафиксирована в [ADR 0001](0001-platform-topology-and-bounded-contexts.md). Есть два самостоятельных, не связанных друг с другом Nginx Gateway:

- **Dev/prod Gateway** (`backend/infra/gateway/nginx.conf`, сервис `gateway` в `backend/docker-compose.yml`) — и в dev-профиле (`docker-compose.dev.yml`: `8080:80`), и в prod-профиле (`docker-compose.prod.yml`: `80:80`) единственный сервис, публикующий порт наружу; `identity-api`/`catalog-api`/`support-api` порты на хост не пробрасывают ни в одном из профилей. Маршрутизирует по текущему `/api/v1/*` контракту на реальные upstream-пути каждого сервиса (в т.ч. `support-service`'s фактический `/api/v1/tickets`, а не `/api/v1/support/*`); отдаёт собственный JSON 404 на нераспознанный путь и `/healthz` для `healthcheck:` без обращения к upstream'ам. Rate limiting (issue #285), anti-spoofing заголовков и `X-Request-ID` (issue #286) — тот же конфиг, поэтому применяются одинаково в обоих профилях. Это осознанный частичный срез Фазы 7b, см. `docs/td-productsflow-microservices-migration.md`.
- **E2E Gateway** (`backend/docker-compose.e2e.yml` + `backend/tests/e2e/nginx.conf`) — остаётся отдельной тестовой инфраструктурой:
  - Session-scoped pytest-фикстура (детали прогона — [ADR 0013](0013-testing-strategy.md)).
  - Strict allow-list публичных путей; проксирует авторизационные и forwarded-заголовки к upstream-сервисам без изменений.
  - E2E-тесты обращаются только к неизменённым публичным BFF-путям через этот Gateway — не к сервисам, БД или брокеру напрямую.
  - Стек полностью удаляется фикстурой (`down -v --remove-orphans`) после прогона; порт Gateway выбирается динамически (свободный TCP-порт), не фиксирован.

Два конфига намеренно не объединены: dev/prod Gateway обслуживает реальный трафик под управлением Docker Compose, E2E Gateway — одноразовый, session-scoped стенд для тестового прогона; смешение целей усложнило бы оба сценария (см. Considered Options).

## Имена Compose-контейнеров определяет проект, не `container_name`

Общий Compose не задаёт `container_name` ни для одного сервиса: Docker Compose формирует имя контейнера из project name и service name автоматически. Это позволяет E2E-фикстуре поднимать полностью изолированный стек под собственным project name (`productsflow-e2e`) и удалять его volumes через `down -v`, не конфликтуя с параллельно запущенным dev-стеком — оба используют одни и те же имена сервисов, но разные project name, значит и разные имена контейнеров. Внутренний DNS по имени сервиса (то, что реально резолвят другие контейнеры) от этого не меняется.

## Considered Options

- **Расширить E2E-Gateway до dev/prod-роли вместо отдельного конфига** — отклонено: E2E-Gateway существует ради строгой изоляции тестового прогона (allow-list, одноразовый стек, динамический порт), не ради маршрутизации боевого трафика; смешение целей усложнило бы оба сценария. Dev/prod Gateway (issue #282/#284) реализован как самостоятельный конфиг и Compose-сервис.
- **`container_name` для читаемости `docker ps`** — отклонено: жёстко зафиксированное имя конфликтует между параллельно запущенными dev- и E2E-стеками на одной машине.

## Consequences

- Любой новый бизнесовый эндпоинт любого из трёх сервисов по умолчанию попадает в `/api/v1` — и в dev/prod Gateway, и в E2E-Gateway allow-list нужно добавить соответствующий `location`, если путь должен быть публично достижим.
- Сами сервисы не знают о существовании ни одного из Gateway и не меняют поведение в их присутствии.
- Параллельный запуск dev/prod-профиля и E2E-прогона безопасен по построению (разные project names → разные имена контейнеров и volumes, разные конфиги и порты Gateway), без ручной координации.
