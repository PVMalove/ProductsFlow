# 0016. Контракт structured logging и точка расширения для OTEL

ADR 0013 уже отвёл под structured-logging и OTEL/metrics bootstrap место в `kernel-platform` — здесь фиксируется, что именно в этом месте лежит. Граница destination протекает по конструкции: содержимое проектируется в Фазах 0–6, а наполняется — в Фазах 8–10, за границей. Ошибка здесь стоит переделки kernel следующим эффортом, поэтому решение фиксирует контракт, а не реализацию.

**Схема JSON-лога стабильна с Фазы 0, значения — нет.** Все 13 полей из перечня TD Фазы 8 (`timestamp`, `level`, `logger`, `message`, `service`, `request_id`, `trace_id`, `span_id`, `actor_id`, `method`, `path`, `status_code`, `duration_ms`) присутствуют в каждой JSON-строке с первого дня. `trace_id`/`span_id` физически нечем заполнить без OTEL-инструментации (Фаза 10) — они зарезервированы как ключи со значением `null`, а не отсутствуют.

**OTEL SDK не подключается.** Ни одна `opentelemetry-*` зависимость не появляется в Фазах 0–6. Точка расширения — два `ContextVar` в kernel-platform, `trace_id_var`/`span_id_var`, по умолчанию `None`; JSON-форматтер читает их так же, как читает `request_id`/`actor_id`. Фаза 10 не переписывает форматтер — она добавляет код (инструментацию или прослойку), который эти переменные заполняет. Формально это оставляет Фазе 10 явную обязанность — заполнить `ContextVar`, а не бесплатно получить значения через API OTEL напрямую в форматтере; это осознанная цена выбора «ноль зависимостей сейчас», а не недосмотр.

**Один ASGI-middleware в kernel-platform устанавливает контекст запроса.** До этого решения одна и та же задача — декодировать bearer и понять, кто действует, — была бы решена трижды: `current_actor_id` в `app/audit.py` (ADR 0004), correlation-id из Фазы 8 TD, JWT-верификация через `IdentityClient`/локальный verifier (ADR 0011, ADR 0013). Вместо этого — один класс `RequestContextMiddleware` в kernel-platform:

- читает `X-Request-ID` (иначе генерирует `uuid4`), выставляет `request_id_var`, возвращает тем же заголовком в ответе (буквальный текст TD Фазы 8);
- принимает в конструкторе `TokenVerifier` — протокол с одним методом верификации токена; identity передаёт локальный verifier (ключ в памяти, ADR 0011), catalog и support передают `IdentityClient.verify_token` (JWKS, ADR 0011/0013). Middleware не знает, какой из них ему подсунули;
- если bearer присутствует и валиден — выставляет `actor_id_var`; если отсутствует или невалиден — не блокирует запрос, `actor_id_var` остаётся `None` (тот же терпимый паттерн, что у нынешнего `actor_context_middleware` в монолите — актуальная авторизация эндпоинта проверяется отдельно, эта прослойка только для audit/логов);
- пишет одну структурную access-log-запись на запрос (`method`, `path`, `status_code`, `duration_ms`) — свой middleware, `uvicorn --no-access-log`, как требует TD;
- сбрасывает оба `ContextVar` в `finally`.

`app/audit.py` (после переноса в домен каждого сервиса, ADR 0004) читает `actor_id_var` из kernel-platform вместо собственного локального `ContextVar` — тот же механизм используется и логированием, и audit-трейлом, без дублирования.

**`actor_id` в лог-строках консьюмера — `null`.** Фоновый воркер, применяющий `user.*.v1` к read-модели, не имеет HTTP-запроса и, соответственно, не имеет инициатора-человека — `null` честно это отражает. Корреляция для этой ветки уже есть без нового поля: `message_id` (равен `outbox_messages.id`, ADR 0014) связывает лог-строки консьюмера друг с другом и с публикацией в identity. **Это решение не относится к вопросу audit-трейла** — устаревшему пункту тумана карты «Actor в audit-логе без HTTP-контекста»: там речь о персистентной записи в `ProductAuditLog`/`UserAuditLog`, здесь — о поле в структурном логе. Формулировка тумана правится отдельно, вопрос остаётся открытым.

**`app/logging_config.py`: цветной вывод остаётся, но переезжает.** TD прямым текстом требует цветной вывод только при `APP_ENV=dev`. Kernel-platform несёт оба форматтера — `JsonFormatter` (дефолт/prod) и обобщённый `ColorFormatter` (текущий класс монолита, без изменений в логике, только смена владельца пакета) — переключение по `settings.app_env`, как сейчас.

## Considered Options

- **Установить OTEL SDK с автоинструментацией FastAPI уже сейчас** — даёт рабочие `trace_id`/`span_id` раньше, без ожидания Фазы 10. Отклонено: тянет зависимость из фазы, лежащей за границей destination, ради спанов, которые сейчас никуда не экспортируются и негде посмотреть (коллектор — тоже Фаза 10/11).
- **Формула форматтера читает `opentelemetry.trace.get_current_span()` напрямую, без своих ContextVar** — технически чище: `opentelemetry-api` (без SDK) — лёгкий пакет, при отсутствии зарегистрированного провайдера отдаёт no-op спаны, и форматтер не пришлось бы трогать в Фазе 10 вовсе. Отклонено при перепроверке уже принятого решения «ноль `opentelemetry-*` зависимостей сейчас» — сохранение выбора важнее локальной технической элегантности; альтернатива фиксируется здесь, чтобы не потерялась к моменту, когда Фаза 10 реально начнётся.
- **Каждый сервис пишет свой middleware против общего контракта ContextVar** — меньше «магии» в kernel, но воспроизводит тройное дублирование, которое и стало поводом для этого решения.
- **`actor_id` консьюмера — синтетический идентификатор** (`"catalog-worker"`) — отличает фоновые строки от `null` по другим причинам, но вводит тип, которого нет в модели `User` (не `int`), и требует отдельного поля/типа-обёртки в схеме лога ради вопроса, который решается фильтром по `message_id is not null`.
- **Прокидывать исходного actor через payload события** — решило бы часть audit-трейл-тумана попутно, но требует расширения схемы события ради поля, которое сейчас нужно только логу. Если audit-трейл когда-нибудь потребует этого — решается тем тикетом, не задним числом здесь.

## Consequences

- Фаза 10 получает точный список того, что нужно сделать: заполнить `trace_id_var`/`span_id_var` из своей инструментации. Явная обязанность, не бесплатное автообнаружение через OTEL API — цена решения «ноль зависимостей сейчас».
- `RequestContextMiddleware` — общая точка отказа наблюдаемости для всех трёх сервисов: баг в нём эквивалентен потере `request_id`/`actor_id`/access-log сразу везде. Приемлемо для витрины, стоит держать в уме при ревью PR, который его вносит.
- `app/audit.py` при переносе в домен сервиса (миграция по доменам, ADR 0010) теряет собственный `ContextVar` — заменяется на импорт из kernel-platform. Небольшая, но реальная правка по сравнению с буквальным копированием текущего файла.
- Пункт тумана карты «Actor в audit-логе без HTTP-контекста» не закрыт этим решением — сужен: то, что происходит с `actor_id` в *логах*, теперь известно; то, что происходит с *audit-трейлом*, остаётся открытым вопросом.
