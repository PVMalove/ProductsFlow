# 0022. Новые сервисы `backend/` не разводят `/api/v1`/`/api/v2` — supersedes ADR 0007

ADR 0007 ввёл `/api/v2` для эндпоинта Картинки, чтобы не менять контракт `/api/v1` монолита для уже существующих клиентов. `catalog-service` создаётся с нуля — у него нет ни одного существующего клиента и ни одной уже выпущенной версии контракта, которую нужно было бы защищать. Причина, ради которой заводилась вторая версия, здесь не применима: разводить `/api/v1`/`/api/v2` для сервиса, стартующего с пустого API, — версионирование ради версионирования.

**Решение.** `catalog-service` (и, если не будет специальной причины на месте, `support-service`) держит один префикс `/api/v1` для всех эндпоинтов, включая Картинку (`GET/POST/DELETE /api/v1/products/{id}/image`). Второй версии нет.

**Область действия.** Касается только новых сервисов `backend/services/*`. Замороженный монолит (`app/`) не переписывается и продолжает обслуживать `/api/v1` и `/api/v2` как есть — ADR 0007 остаётся верным описанием его текущего состояния, просто помечается superseded для новых сервисов.

## Consequences

- Видимость Товара (правила ADR 0002/0003) и логика Картинки живут в одном роутере `/api/v1/products`, а не разнесены по двум версиям — общий модуль проверки видимости, который ADR 0007 явно выносил ради переиспользования между `/v1` и `/v2`, здесь не нужен вовсе: переиспользовать не с чем.
- Если у `catalog-service` когда-нибудь появится реальная причина не ломать уже выпущенный `/api/v1` (внешние клиенты, мобильное приложение и т.п.), решение о второй версии принимается заново, с этим новым основанием — не реанимацией ADR 0007 «по умолчанию».
