# 0011. Раздача публичного ключа identity через JWKS

После распила проверка JWT перестаёт быть внутренним делом одного процесса: identity выпускает токены, а catalog и support обязаны проверять подпись локально, не обращаясь к identity на каждый запрос (TD §4.1). Алгоритм RS256 и «приватный ключ только у identity» зафиксированы в TD; здесь решается, как публичная половина попадает к потребителям. identity публикует `GET /.well-known/jwks.json` — открытый, без аутентификации, как того требует стандарт: публичный ключ не секрет. catalog и support кэшируют ответ с TTL и выбирают ключ по `kid` из заголовка токена. `kid` вычисляется как JWK thumbprint (RFC 7638), то есть детерминированно выводится из самого ключа — это делает его стабильным между рестартами identity и одинаковым у всех реплик, без чего кэш потребителей обесценивался бы при каждом перезапуске.

Состав решения:

- **Кэш.** TTL плюс внеочередной refetch при неизвестном `kid`, с троттлингом окна. Дефолты: TTL 10 минут, окно троттлинга 60 секунд — параметры конфигурации, тюнингуются без пересмотра решения.
- **Старт.** Предзагрузка JWKS при запуске не фатальна: неудача логируется и не блокирует старт, дальше работает ленивое обновление. Порядок запуска сервисов остаётся свободным.
- **Ротация.** `kid` присутствует в каждом токене с самого начала, но вторая пара в Фазах 0–6 не заводится. Это задел: добавить ключ позже можно без инвалидации живых токенов.
- **Claims.** К `sub`, `iat`, `exp` добавляется `iss`. `aud` не вводится — все три сервиса сейчас равноправные получатели.
- **Приватный ключ.** Файл по пути из `IDENTITY_JWT_PRIVATE_KEY_PATH`; том монтируется только в identity.
- **Генерация.** Цель `make keys` создаёт пару; ключи в git не попадают. В CI генерируется эфемерная пара на прогон — так же, как сейчас поступают с `SECRET_KEY`.
- **Fail-fast.** При `APP_ENV=prod` пустые приватный ключ, JWKS-URL, `DATABASE_URL` или `ADMIN_PASSWORD` валят старт с внятной ошибкой. В dev дефолты допускаются, чтобы сценарий «склонировал и запустил» продолжал работать.

## Considered Options

- **PEM в переменной окружения** (`IDENTITY_JWT_PUBLIC_KEY`) — самый дешёвый вариант: ноль сетевых зависимостей, fail-fast получается даром, ротация сводится к рестарту. Отклонено в пользу отраслевого стандарта: цель эффорта — витрина, и JWKS есть то, что ожидает увидеть читающий код. Цена — новая связанность на старте — признана приемлемой осознанно.
- **Файл через общий том compose** — без сети и без многострочного PEM в `.env`. Отклонено: вводит том, разделяемый между тремя сервисами, что противоречит духу data-per-service, ради экономии, которой JWKS не требует.
- **Refetch на каждый неизвестный `kid` без троттлинга** — максимально отзывчиво к ротации. Отклонено: превращает поток токенов с выдуманным `kid` в усилитель запросов на identity.
- **Только TTL, без внеочередного refetch** — неуязвимо к тому усилению и проще всего. Отклонено: при ротации даёт окно отказов длиной в целый TTL.
- **Fail-fast на старте при недоступном JWKS** — проще рассуждать о состоянии системы. Отклонено: вводит жёсткий порядок запуска и роняет catalog с support при каждом рестарте identity.
- **Случайный UUID в роли `kid`** — отклонено: `kid` становится вторым артефактом, который надо хранить синхронно с ключом и раздавать отдельно, и легко разъезжается между репликами.
- **Полная ротация с overlap двух пар** — правильна для прода. Отклонено как избыточная для Фаз 0–6, где живых пользователей нет; наличие `kid` с самого начала оставляет дверь открытой.
- **`aud` в токене** — отклонено: сейчас три сервиса равноправны как получатели, различать их нечем, и claim был бы декорацией.

## Consequences

- Появляется связанность catalog и support → identity на старте и при обновлении кэша, которой при PEM в переменной окружения не существовало. Проверка подписи при этом остаётся локальной и не ходит по сети на каждый запрос — посылка TD §4.1 не нарушена.
- Троттлинг внеочередного refetch — не оптимизация, а защита. Без него один токен с выдуманным `kid` стоит потребителю одного HTTP-запроса к identity.
- Верифицировать токены обязаны все три сервиса, включая анонимные пути: `actor_context_middleware` декодирует bearer именно ради `actor_id` для audit-лога (ADR 0004). JWKS-клиент поэтому нужен везде — это первый конкретный кандидат в `common-kernel`, решение о котором принимается отдельно.
- identity проверяет собственные токены локально по ключу в памяти, без HTTP-вызова к своему же JWKS-эндпоинту.
- Константа `ALGORITHM = "HS256"` и участие `settings.secret_key` в подписи токенов исчезают.
- Токены, выпущенные монолитом, в новой системе невалидны. Задачи миграции токенов не существует: монолит не работает параллельно с сервисами (ADR 0010).
- Новых зависимостей RS256 не требует — `cryptography` уже объявлена прямой зависимостью в `pyproject.toml`, хотя в коде монолита не импортируется ни разу.
- Fail-fast охватывает не только JWT: техдолг №2 TD закрывается целиком, включая пустые `DATABASE_URL` и `ADMIN_PASSWORD` при `APP_ENV=prod`.
