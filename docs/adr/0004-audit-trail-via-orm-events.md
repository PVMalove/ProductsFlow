# 0004. Audit trail через ORM event listeners с ContextVar для actor

Каждая мутация `User`/`Product` (создание/изменение/удаление/(де)активация) должна попадать в audit-лог вместе с Инициатором действия (Actor) — id пользователя, который её выполнил (см. `CONTEXT.md`). Вместо явных вызовов логирования в `ProductRepository`/`UserRepository`/роутерах, audit-записи вставляются из SQLAlchemy ORM event listeners (`after_insert`/`before_update`/`before_delete` в `app/audit.py`) — так гарантируется, что ни один путь мутации не забудет залогировать действие, включая будущие. Внутри ORM-листенера нет доступа к HTTP-запросу, поэтому Actor прокидывается туда через `ContextVar` (`current_actor_id`), которую выставляет HTTP-мидлварь (`actor_context_middleware`, `app/main.py`) из bearer-токена запроса; при отсутствии HTTP-контекста (саморегистрация, `seed_db()`) listener использует id самой затронутой строки (`target.id`/`target.user_id`) как Actor.

## Considered Options

- **Явные вызовы audit-логирования** в repository/router-методах (например, отдельный вызов после каждого мутирующего `commit`). Отклонено — легко забыть в новом мутирующем методе; ORM-события покрывают все пути мутации автоматически, включая будущий код, который трогает эти модели напрямую через ORM.

## Consequences

- Actor — неявное состояние (`ContextVar`), а не обычный параметр функции: читателю repository-кода не видно ни того, что мутация параллельно пишет audit-запись, ни того, откуда берётся Actor.
- Любая мутация вне HTTP-запроса (сидинг, скрипты, будущие фоновые задачи) молча получает в качестве Actor саму затронутую строку (Владельца товара или самого пользователя), а не `system`/`None` — это нужно учитывать, если появится настоящий фоновый процесс, мутирующий чужие записи.
- `ProductAuditLog.product_id` намеренно без `ForeignKey` (см. комментарий в `app/models.py`) — иначе `before_delete`-листенер не смог бы вставить строку audit-лога для только что удаляемого товара при включённых внешних ключах.
