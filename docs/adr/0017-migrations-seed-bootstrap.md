# 0017. Миграции, сид и bucket-ensure: bootstrap-шаг вместо lifespan

Техдолг №5 TD (`run_migrations()`/`seed_db()` в `lifespan` — гонка при нескольких репликах) TD чинит в Фазе 7, за границей destination. Но три сервиса со своим `alembic/` рождаются в Фазах 2, 4, 5 — внутри границы — и без явного решения унаследуют дефект трижды. ADR 0010 уже подготовил место: `docker-compose.migrations.yml` в дереве workspace, с явной пометкой «решение по механизму принимается отдельно (техдолг №5 TD)» — это решение.

**Один bootstrap-шаг на сервис: миграции + bucket-ensure (только catalog) + сид, последовательно.** `identity-bootstrap`, `catalog-bootstrap`, `support-bootstrap` — one-off compose-сервисы, `depends_on: <своя db> healthy`. `*-api` каждого сервиса — `depends_on: <свой>-bootstrap: condition: service_completed_successfully`. Три bootstrap-шага не зависят друг от друга и могут выполняться параллельно — на этом построен и сид (см. ниже). Порядок внутри catalog-bootstrap: `alembic upgrade head` → `ensure_minio_buckets` → сид. Тот же порядок, что сейчас в `lifespan`, просто вынесенный из процесса API.

**`ensure_minio_buckets` перестаёт быть частью API-процесса.** Блокирующая проблема старта существует с Фазы 4, а не с Фазы 13, как формулирует TD (там речь о таймаутах/circuit breaker — устойчивость к *частичной* недоступности, не о самом факте блокировки старта). Если MinIO недоступен во время bootstrap-шага — шаг завершается ошибкой, compose не поднимает `catalog-api`. Жёсткий отказ на деплое, не деградация в рантайме: устойчивость к недоступности MinIO во время работы сервиса — предмет Фазы 13, за границей.

**Advisory lock не нужен.** Гонка, которую он должен был бы предотвращать, — параллельный `alembic upgrade`/сид от нескольких *реплик API*. One-off структура эту гонку убирает по построению: bootstrap-шаг ровно один, реплицируется только `*-api`, который стартует уже после успешного завершения bootstrap. Alembic сам по себе идемпотентен (отслеживает применённые ревизии в своей таблице), сид идемпотентен через существующий паттерн «проверить count, если больше нуля — пропустить». Повторный запуск bootstrap (ручной перезапуск, ретрай CI) безопасен без отдельного механизма блокировки.

**Локальная разработка — Makefile-цепочка, не условный код в `lifespan`.** `make dev pkg=identity-service` последовательно вызывает `alembic upgrade head`, затем `uvicorn --reload`. FastAPI-приложение никогда не выполняет миграции само — ни в dev, ни в prod, один код-путь без `if settings.app_env == "dev"` в самом приложении. `CLAUDE.md` переписывается в Фазе 0 (уже отмечено как предстоящая правка в ADR 0010) — вместо обещания «перед `uvicorn` ничего запускать не нужно» описывает `make dev pkg=<сервис>`.

**Сид — независимый по сервисам, координация через фиксированный `id`, без межсервисного вызова.** identity сидирует admin-пользователя первой строкой в чистой БД — `id=1` детерминирован автоинкрементом Postgres на пустой таблице. catalog сидирует 360 товаров с `user_id=1` **и в том же сид-скрипте** пишет собственную строку `OwnerReadModel(user_id=1, role=ADMIN, is_active=True)` — не через событие `user.registered.v1` и не через `IdentityClient`, а напрямую, тем же кодом, что создаёт демо-товары. Обход событийного конвейера для сида — осознанное упрощение: сид детерминирован и контролируем, ждать доставки события ради собственных сидовых данных незачем. Именно поэтому три bootstrap-шага не нуждаются в зависимости друг от друга — конвенция статична (`id=1`), не рантайм-вызов.

**support не сидируется.** TD не описывает демо-обращений; пустая таблица `Conversation` — легитимное начальное состояние, ничто в карте от сид-данных support не зависит.

**Fail-fast `ADMIN_PASSWORD`** уже закрыт ADR 0011 (`APP_ENV=prod` валит старт на пустом секрете) — здесь не пересматривается, сид просто читает уже провалидированное значение.

## Considered Options

- **Оставить миграции/сид в `lifespan` на Фазы 0–6, переделка — позже** — отклонено: три сервиса унаследовали бы известный дефект трижды безо всякой причины, при том что место под фикс (`docker-compose.migrations.yml`) уже подготовлено ADR 0010 именно под это решение.
- **`pg_advisory_lock` вокруг `alembic upgrade` внутри `lifespan`, реплики остаются** — отклонено: сохраняет миграции внутри API-процесса, то есть сохраняет и блокировку старта, которую призван решить весь этот тикет; advisory lock решил бы только гонку, не задержку.
- **Условный код в `lifespan`** (`if app_env == "dev"`) для сохранения удобства локальной разработки — отклонено: два разных поведения одного и того же кода в зависимости от окружения — источник багов «работает в dev, не работает в prod» и обратного. Makefile-оркестрация даёт то же удобство без ветвления в самом приложении.
- **Сид через реальный межсервисный вызов** (catalog ждёт identity, читает настоящий `user_id` через API или напрямую из БД) — отклонено как избыточное для bootstrap-сценария: даёт точный результат ценой синхронной межсервисной зависимости на старте — ровно то, чего ADR 0012 старается избегать в рантайме, здесь незачем вводить ради одноразового шага.
- **Только identity сидируется, catalog/support стартуют пустыми** — отклонено: цель эффорта — витрина (Notes карты), пустой каталог на демонстрации слабее, чем работающий пример владения и видимости.
- **Отдельные one-off сервисы на каждый под-шаг** (`*-migrations`, `*-seed`, `*-bucket-ensure` раздельно) — отклонено: гранулярнее для отладки, но плодит compose-сервисы и цепочки `depends_on` ради шагов, которые физически всегда выполняются вместе и в одном порядке.

## Consequences

- Три bootstrap-шага параллелизуемы и не имеют `depends_on` друг на друга — прямое следствие того, что сид координируется конвенцией (`id=1`), а не рантайм-вызовом. Если конвенция когда-нибудь изменится на реальный кросс-сервисный вызов, эта независимость исчезнет вместе с ней.
- Читаемость демо-данных полагается на то, что БД действительно пустая при первом запуске — фиксированный `id=1` для admin не гарантирован, если строки в `users` уже существовали до сида (сценарий пересидирования непустой БД не рассматривается: текущая идемпотентность — «пропустить, если count > 0» — уже подразумевает однократный сид на чистую БД).
- `CLAUDE.md` получает второе расхождение с реальностью, требующее правки в Фазе 0 (первое — из ADR 0010): обещание «миграции не нужно запускать вручную» заменяется на явную Makefile-команду.
- Отказ MinIO на bootstrap-шаге — жёсткий стоп деплоя catalog, без деградации. Это временное поведение до Фазы 13, а не окончательное — там же появится circuit breaker и осмысленная деградация (`image_url=null` вместо отказа).
- `ensure_minio_buckets`, вызываемый из bootstrap-скрипта, а не из FastAPI-приложения, теряет доступ к DI-контейнеру приложения — по факту он и сейчас не использует ничего специфичного для FastAPI, перенос механический.
